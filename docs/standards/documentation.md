# 文档规范

本文是 OpsKeeper 文档组织、编写、验收和归档的强制性规范。所有新增文档、需求、任务和验收记录都必须遵循本文；特殊情况需要在 ADR 或对应迭代文档中说明原因。

## 1. 文档原则

1. **一个事实只有一个权威位置。** 其他文档使用链接引用，不复制会持续变化的规则、配置或状态。
2. **区分当前事实与历史记录。** `design/` 描述当前项目设计事实，`iterations/` 保存某次迭代的范围、任务和验收历史。
3. **规划和验收分离。** 需求文档说明要交付什么；需求验收报告只记录已经执行的验证和结果，不把未来计划写成已完成事实。
4. **项目级与迭代级分离。** 架构、工程规范、ADR、指南和 Runbook 跨迭代维护；需求和任务属于具体迭代。
5. **历史迭代只读。** 迭代封板后整体移动到 `iterations/archived/`。如需纠错，只追加勘误或 ADR，不覆盖原验收结论。
6. **证据可复核。** 验收记录必须给出命令、测试、页面路径、提交、CI 运行或外部环境记录；不要只写“已验证”。
7. **文档先于范围扩张。** 新增需求必须先建立需求文档和任务清单，再开始实现；超出需求边界的工作应进入新需求或 backlog。
8. **链接优先于复制。** 移动或重命名文档时，必须同步更新 README、相关设计文档和全仓库引用。
9. **言简意赅，条理清晰。** 使用准确、简洁的表述组织内容，避免冗余和歧义。

## 2. 目录职责

```text
docs/
├── README.md                       # 文档总入口
├── backlog.md                      # 跨迭代待规划事项和技术债
├── known-limitations.md            # 当前版本限制和容量边界
├── design/                         # 项目级当前设计事实
├── adr/                            # 长期架构决策及其历史
├── standards/                      # 强制工程和文档规则
├── guides/                         # 可执行的开发、使用和交付步骤
├── runbooks/                       # 生产故障、恢复和应急处置
├── iterations/                     # 迭代需求、任务和验收
│   ├── Ixxx-name/                  # 当前迭代，最多一个
│   │   ├── iteration.md
│   │   ├── Rxxx-requirement.md
│   │   └── Rxxx-requirement-acceptance.md
│   └── archived/                   # 已封板迭代
└── templates/                      # 新建文档模板
```

`design/` 下不再建立 `domain/` 子目录；领域设计文档直接放在 `design/` 下。`guides/` 和 `runbooks/` 直接位于 `docs/` 下，`runbooks/` 不需要 README 索引文件。ADR 的 README 是例外，因为它是 ADR 编号索引和状态约定。

## 3. 迭代、需求和任务模型

### 3.1 迭代

当前迭代直接放在 `docs/iterations/` 下，目录名使用 `Ixxx-short-name`。迭代封板后，将整个目录移动到 `docs/iterations/archived/`，目录内容和文件名不变。

一个迭代目录只包含一个 `iteration.md` 和若干需求文件。`iteration.md` 直接包含需求清单、需求目标、任务总览、依赖、风险、进入条件、退出条件和封板结论，不再创建独立的 `requirements.md`。

### 3.2 需求

每个需求使用两个同级文件：

```text
R001-requirement.md
R001-requirement-acceptance.md
```

需求文档必须包含背景、目标、范围、非目标、任务清单、依赖、风险和统一验收标准。需求验收报告必须包含需求结论、任务验收汇总、每个任务的验收小节、遗留事项和用户确认。

### 3.3 任务

任务只作为需求文档和需求验收报告中的章节存在，不创建 `T01.md` 这类顶层文件。任务编号在需求内从 `T01` 开始；跨文档引用使用完整标识 `I001-R001-T01`。

## 4. 状态和封板规则

迭代状态：`规划中`、`实施中`、`待封板`、`已封板`。
需求状态：`待规划`、`实施中`、`待验收`、`已完成`、`阻塞`。
任务状态：`待批准`、`实施中`、`待验收`、`已完成`、`阻塞`。

封板前必须满足：

- 迭代内所有需求均已完成或明确记录为阻塞；
- 已完成需求下的任务均有验收结果和证据；
- 需求验收报告记录用户确认和遗留事项；
- `iteration.md` 记录封板日期、提交基线和最终结论；
- 未完成事项已经转入 `backlog.md` 或下一迭代。

封板后不得继续在该迭代目录增加新需求。新范围必须创建新的迭代或需求。

## 5. 命名、链接和证据

- 迭代目录：`Ixxx-short-name/`，例如 `I002-access-improvements/`。
- 需求规划：`Rxxx-requirement.md`。
- 需求验收：`Rxxx-requirement-acceptance.md`。
- 任务引用：`Ixxx-Rxxx-Txx`，例如 `I001-R001-T03`。
- 文件使用小写 ASCII、短横线分隔；中文标题可以写在 Markdown 一级标题中。
- 需求和验收文件只保留可复核的关键证据，不复制大段 CI 原始日志；原始日志使用提交、运行地址或外部记录引用。
- 相对链接必须以当前文件位置计算，并在移动文件后重新检查。

## 6. 模板使用

新建迭代时复制 `templates/iteration.md`，新建需求时复制 `templates/requirement.md`，新建验收报告时复制 `templates/requirement-acceptance.md`，然后按命名规则重命名。模板中的占位符必须在提交前替换或删除。
