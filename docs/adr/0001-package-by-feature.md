# ADR-0001：Go 后端采用模块化单体和按业务特性组织

- 状态：已接受
- 日期：2026-08-15

## 背景

OpsKeeper 同时包含组织、身份、授权、资源、诊断和巡检等业务能力，但当前团队规模和部署需求不需要微服务。后端还需要保持 Go 代码直接、显式，避免按 Java 风格预先建立全局 Controller、Service、Repository 和 Adapter 层级。

## 候选方案

1. 按技术层建立全局 `model/`、`service/`、`repository/` 和 `adapter/`。
2. 每个业务能力拆成独立服务和独立仓库。
3. 保持模块化单体，按业务特性建包，特性专属类型、规则、Store 和测试留在同一个包。

## 决定

采用方案 3。Go 后端按业务特性组织，例如 `organization/`、`identity/` 和 `authorization/`。特性专属 PostgreSQL Store 可以直接放在该特性包的 `store.go`，不建立全局 Adapter 或 Repository 层。

HTTP 是独立协议边界，进程入口位于 `cmd/`。数据库连接生命周期、缓存客户端或消息传输只有在出现真实的跨特性需求时才建立共享基础设施包。接口由消费者在需要测试替身或多个真实实现时定义，不为每个类型机械创建接口。

## 影响

- 业务代码和测试具有清晰的局部性，新增能力不需要穿越多层目录。
- 单个特性包可能同时包含业务规则和持久化实现，需要通过文件和依赖方向保持职责清楚。
- 当特性边界确实需要独立部署时，可以从模块化单体中提取；在此之前不承担分布式事务和服务治理成本。
- 工程约束以[Go 编码与工程组织通用规范](../standards/go-coding-conventions.md)为准。
