# I006-R001 统一通知机制

**迭代：** I006-notification-mechanism
**需求状态：** 实施中
**验收报告：** [R001-requirement-acceptance.md](R001-requirement-acceptance.md)

## 1. 需求背景

当前通知能力嵌在巡检模块中，仅支持 HTTPS Webhook。通知渠道、规则和模板没有独立的领域边界；巡检结果提交后才创建投递，恢复事件没有完整进入通知链路，重复打开异常可能按巡检窗口重复发送，失败投递也缺少明确的最终失败和人工恢复语义。当前页面也把渠道配置和巡检策略混在一起，无法复用通知定义。

本需求建立通知中心，并保留巡检策略作为通知规则的使用方。通知中心负责“发什么、发给谁、用什么格式、如何投递”；巡检策略负责“哪些巡检使用哪些规则”。

## 2. 目标

- 增加位于权限菜单上方的通知菜单和通知页面；
- 统一管理通知渠道、通知模板、通知规则和投递记录；
- 默认支持锁定 Notify/Go-Notify 版本公开的全部 provider，通过 provider 注册表向前端暴露字段和能力；
- 使渠道凭据安全、可测试、可启停、可限流，且不独立成共享凭据对象；
- 以事件状态变化触发通知，支持异常打开、重新打开、级别变化、恢复、运行失败和能力不可用；
- 支持模板复用、版本冻结、变量校验、预览和 provider 特定格式转换；
- 支持事件筛选、级别过滤、目标过滤、冷却、聚合、静默时段和多渠道路由；
- 保证巡检状态、通知事件和投递任务在一个 PostgreSQL 事务中提交；
- 默认使用 PostgreSQL 原生队列，并通过 `OPSK_MESSAGE_QUEUE_BACKEND=postgres` 明确选择当前唯一支持的后端；
- 提供可靠投递、幂等、有限重试、死信、人工重试、审计和可观测性。

## 3. 范围

### 3.1 领域对象和职责

| 对象 | 权威职责 | 是否可复用 |
|---|---|---|
| NotificationChannel | provider 类型、Scope、名称、启停、限流、加密配置和配置版本 | 可被多个规则引用 |
| NotificationTemplate | 标题/正文/结构化 payload 模板及不可变发布版本 | 可被多个规则路由引用 |
| NotificationRule | 事件、级别、目标、冷却、聚合、静默和渠道/模板路由 | 可被多个巡检策略引用 |
| InspectionPolicyNotificationRule | 巡检策略与规则的关联 | 只表达使用关系，不复制规则内容 |
| NotificationEvent | 已发生的状态变化及不可变事件数据 | 由巡检事务产生 |
| NotificationDelivery | 某事件经过某规则路由到某渠道的一次投递生命周期，同时承担事务事实记录和 PostgreSQL 队列行 | 可重试、可审计 |
| NotificationDeliveryAttempt | 单次外部发送的结果、状态和脱敏错误 | 只追加，不覆盖历史尝试 |

渠道、模板和规则都有 `scope_id`。默认只在所属 Scope 可见；管理员显式开启对子 Scope 可用后，下级 Scope 才能选择。跨团队不继承。删除采用软删除或停用，已生成的投递快照仍可完成发送，渠道密钥清除后不再允许发送并进入明确失败状态。

### 3.2 通知事件

首期事件类型固定为：

| 事件 | 触发条件 | 默认状态 |
|---|---|---|
| `finding.opened` | 持续身份首次出现 | 通知 |
| `finding.reopened` | 已恢复身份再次出现 | 通知 |
| `finding.severity_changed` | 同一身份的严重级别变化 | 通知 |
| `finding.resolved` | 成功观察不再返回该身份 | 通知 |
| `inspection.failed` | 巡检运行最终失败 | 通知 |
| `inspection.degraded` | 确定性检查完成但解释或可选能力不可用 | 可选 |
| `notification.test` | 管理员主动测试渠道或规则 | 只发送测试，不进入巡检统计 |

事件由后端依据旧值和新值计算。重复观察同一个仍打开、级别不变的 Finding 不产生事件；冷却和聚合由规则进一步控制。事件正文只包含声明变量所需的脱敏事实，不包含资源凭据、Authorization Header、完整连接配置或任意模型上下文。

### 3.3 渠道和 provider

渠道配置由 provider 注册表描述：`kind`、显示名称、字段 Schema、秘密字段、测试方法、速率限制能力、消息格式能力和最大 payload。前端按 Schema 生成表单，后端再次校验。Notify/Go-Notify 只负责 provider 发送适配，不拥有 Scope、规则、模板、审计或重试状态。

首期 provider 清单以锁定依赖版本的公开 provider 为准，构建时生成可审计的 provider 矩阵；未编译进当前版本的 provider 不在页面伪造为可用。新增 provider 必须补充契约测试、字段脱敏和错误分类。HTTPS Webhook 继续支持签名、超时、响应体上限和限流。

凭据使用项目现有密文保护方案，在 `notification_channels` 的 provider 配置中加密保存；API 只返回字段名、是否已配置和脱敏摘要。测试发送使用当前保存配置或一次性草稿配置，草稿不会提前写入渠道。

### 3.4 模板

模板是通知页面中的独立可复用对象，按版本发布。每个版本包含名称、格式（文本/Markdown/JSON）、标题、正文或 payload、变量声明、内容哈希、状态和创建者；已发布版本不可原地修改，编辑生成新草稿版本。

模板只允许受限变量，例如事件类型、严重级别、规则名、策略名、资源名称、Scope 名称、Finding 摘要、首次/最近观察时间、运行链接和 OpsKeeper 链接。变量缺失、类型不符或输出超过 provider 限制时，投递在发送前失败并记录可操作错误。模板不能执行代码、访问数据库、读取未声明字段或调用工具。

### 3.5 规则和巡检关联

规则配置包括：事件类型、最低严重级别、Scope/资源过滤、渠道与模板路由、冷却窗口、聚合窗口、最大批量、静默时段、启停和失败策略。规则可以引用多个渠道；同一事件到多个渠道分别生成投递并分别限流。

巡检策略只保存规则 ID 的多对多关联。规则编辑后影响后续事件；已经写入投递队列的事件使用创建时的规则、模板版本和渠道配置快照。策略创建页面提供规则选择器和“新建规则”快捷入口，但规则权威页面仍是通知中心。

### 3.6 PostgreSQL 默认消息队列

当前项目使用 `pgx/v5`，可在专用连接上执行 `LISTEN` 并调用 `WaitForNotification`；不需要增加 PostgreSQL 扩展。实现采用以下组合：

1. 巡检状态变化、`notification_events` 和每渠道一条、带不可变路由快照的 `notification_deliveries` 在同一事务中写入；事务内调用 `pg_notify('opskeeper_notification', '')`，PostgreSQL 仅在事务提交后发出唤醒信号。
2. Worker 使用 `notification_deliveries` 的状态、`available_at`、租约和 `FOR UPDATE SKIP LOCKED` 并发领取，不在事务锁内执行网络请求。
3. Worker 持有独立监听连接以低延迟唤醒；监听连接断开、通知合并或 payload 丢失时，按 `OPSK_NOTIFICATION_QUEUE_POLL_INTERVAL` 轮询兜底。
4. 租约过期可重新领取；每次发送按 `delivery_id` 和幂等键记录，外部响应只保存限长、脱敏结果。
5. 失败按 Retry-After、指数退避和最大尝试次数处理，耗尽后标记 `dead_letter`，支持有权限用户手动重试并生成新的审计记录。

`LISTEN/NOTIFY` 本身不是持久化队列，不能替代表记录。当前 Go `pgx/v5` 支持在独立连接上 `LISTEN` 和 `WaitForNotification`，无需额外驱动或扩展。`pgmq` 可作为未来独立 ADR 的候选，但当前不选用：它不是 PostgreSQL 内置能力，当前 `postgres:16-alpine`/生产数据库不保证安装，迁移角色也不应拥有创建实例级扩展权限；普通表队列已满足当前通知负载、审计和恢复需求。

### 3.7 队列配置

```text
OPSK_MESSAGE_QUEUE_BACKEND=postgres
```

该变量为空时按 `postgres` 处理；当前服务只接受 `postgres`，配置其他值应在启动校验阶段明确报错。未来新增队列后端时，必须先完成独立 ADR、容量评估、数据一致性边界、健康检查和迁移/回滚设计，不在本需求中预留第二套实现。

### 3.8 权限、API 和审计

新增通知权限：`notification:read`、`notification:manage`、`notification:test`、`notification:retry`。规则关联巡检策略还需要现有 `inspection:manage`，读取投递记录同时检查通知 Scope 可见性。内置角色按平台、团队、项目继承规则补充最小权限；前端不自行推断权限，所有写入和测试请求由后端重新校验 Scope。

API 采用当前 `/api/v1` 风格，至少包括：

- `GET/POST/PATCH/DELETE /notification-channels`；
- `POST /notification-channels/{id}/test`；
- `GET/POST/PATCH/DELETE /notification-templates`、`/notification-templates/{id}/versions`、`/preview`；
- `GET/POST/PATCH/DELETE /notification-rules`、`/notification-rules/{id}/test`；
- `GET /notification-deliveries`、`POST /notification-deliveries/{id}/retry`；
- `GET/PUT /inspection-policies/{id}/notification-rules`。

凭据字段永不回传；错误响应不泄漏 provider 原始密钥或完整响应。渠道变更、模板发布、规则变更、测试发送、重试和死信操作均写审计。日志只记录 provider、scope、delivery ID、状态、次数和分类错误。

### 3.9 前端页面

新增 `frontend/src/features/notification/NotificationPage.svelte`，由 `App.svelte` 负责菜单和页面装配，页面专属请求和纯函数放在 notification feature 目录。页面包含四个可折叠区域或选项卡：渠道、模板、规则、投递记录；默认进入渠道列表，并在标题栏提供创建按钮和当前 Scope 说明。

实现前必须在 `frontend/preview/notification-page-options-preview.html` 提供至少三种完整候选方案，真实展示渠道表单、规则路由、模板预览、投递状态、空状态、错误和无权限状态；用户确认后才冻结一种方案。页面必须遵循前端 UI 规范的主题令牌、键盘路径、原地校验、加载/失败/成功状态、窄屏滚动和敏感字段显示规则。

## 4. 非目标

- 不把通知规则或模板写入 Skill 正文、Provider 配置或巡检目标快照；
- 不支持模板内任意脚本、表达式执行、数据库查询或工具调用；
- 不在本需求中实现外部消息队列、Relay 或其他队列后端；
- 不在发送网络调用期间持有 PostgreSQL 事务锁；
- 不新增默认外部消息队列、pgmq 或其他平台中间件服务；
- 不在首期实现短信计费、联系人订阅中心、值班排班或自动处置。

## 6. 任务说明

### T01 通知领域与事务事件

#### 目标

建立通知模块唯一的数据和事件边界，使巡检状态、事件和投递任务原子提交。

#### 实施范围

- 新增渠道、模板、版本、规则、策略关联、事件、投递和尝试表及约束；
- 从 Finding upsert 的旧状态/新状态计算事件；覆盖 opened、reopened、severity_changed、resolved；
- 将运行最终失败和能力不可用转换为统一事件；
- 在一个事务内写入巡检结果、Finding 状态、事件和待路由投递任务；
- 设计幂等键、快照哈希、软删除/停用和 Scope 共享约束；
- 删除或迁移旧通知路径，避免提交后单独入队的双方案。

#### 验收标准

- 事务任一步失败时，巡检结果和通知事件都不落库；
- 重复 Worker 或重复结果不会生成重复事件；
- 未变化的持续 Finding 不生成通知；恢复事件包含原始 Finding 身份；
- 约束能阻止跨 Scope 越权关联、重复名称和无效状态。

#### 风险和回滚

迁移可能影响已有 Webhook 投递记录。先增加新结构和数据校验，再切换写路径；切换前保存旧记录映射，失败时停止新通知写入但不删除巡检事实。

### T02 Provider 注册与通知渠道

#### 目标

把 Notify/Go-Notify provider 统一纳入可验证、可脱敏的渠道目录。

#### 实施范围

- 锁定依赖版本并生成 provider 支持矩阵；
- 定义 provider 注册契约、字段 Schema、秘密字段、测试和消息转换能力；
- 渠道创建、编辑、停用、恢复、删除、限流和配置版本；
- 加密保存秘密字段，API 只返回脱敏摘要；
- 测试发送使用草稿或已保存配置，不把草稿提前写库；
- 对 HTTPS、证书校验、超时、响应大小和 Retry-After 进行统一限制。

#### 验收标准

- 每个公开 provider 都能显示准确配置字段或明确标注当前构建不支持；
- provider 配置不合法、秘密缺失和权限不足在服务端拒绝；
- 渠道详情、日志和错误均不泄漏凭据；
- 渠道限流按渠道隔离，测试发送不能绕过限流和审计。

#### 风险和回滚

第三方 provider 行为差异大。以 provider 契约测试和独立适配文件隔离，首期保留 HTTPS Webhook 作为基线；单个 provider 失败不影响其他渠道。

### T03 模板版本与安全渲染

#### 目标

提供可复用、可预览、不可变且不会执行任意代码的通知模板。

#### 实施范围

- 模板和版本的草稿/发布/停用状态；
- 受限变量 Schema、类型校验、缺失变量检查和输出大小限制；
- 文本、Markdown、JSON 三种格式及 provider 转换；
- 预览使用模拟事件，不读取真实凭据和未声明字段；
- 发布版本生成内容哈希，投递保存版本快照。

#### 验收标准

- 已发布版本不能原地修改；
- 非法变量、模板注入、超限输出和不兼容 provider 被拒绝；
- 相同输入和版本得到稳定输出；
- 预览与实际投递渲染使用同一渲染函数。

#### 风险和回滚

模板语法变化可能影响历史消息。发布版本不可变，回滚只需重新选择旧版本，不覆盖正文。

### T04 规则匹配与巡检关联

#### 目标

把事件筛选和通知路由从巡检代码中抽离，并让规则可跨策略复用。

#### 实施范围

- 事件类型、严重级别、Scope/资源过滤、渠道/模板路由；
- 冷却、聚合、最大批量、静默窗口和重复事件去重；
- 巡检策略与规则多对多关联、可见性和权限校验；
- 规则命中后生成路由快照，不在 Worker 发送时重新解释历史规则；
- 新建策略快捷创建规则，但保留通知页作为唯一管理入口。

#### 验收标准

- 同一事件按规则匹配结果生成正确的多渠道投递；
- 冷却和聚合不会吞掉恢复事件或跨事件错误合并；
- 规则和策略 Scope 不可越权；
- 修改规则只影响后续事件，已入队投递保持快照。

#### 风险和回滚

规则条件过多会增加解释复杂度。首期使用结构化字段和白名单条件；未知条件拒绝保存，不采用自由表达式执行。

### T05 PostgreSQL 队列与可靠投递

#### 目标

提供 PostgreSQL 持久化队列，保证至少一次、可重试、可观测的通知投递。

#### 实施范围

- PostgreSQL `notification_deliveries` 表队列、事务写入、`FOR UPDATE SKIP LOCKED`、租约和 `LISTEN/NOTIFY`；
- `pgx/v5` 专用监听连接、断线重连和轮询兜底；
- Worker、幂等键和路由快照校验；
- 指数退避、Retry-After、最大尝试、死信、手动重试和限流；
- `OPSK_MESSAGE_QUEUE_BACKEND` 的启动校验、健康指标和积压指标。

#### 验收标准

- PostgreSQL 模式在通知唤醒丢失、Worker 崩溃、租约过期和多 Worker 并发下不丢事件且不重复完成；
- `OPSK_MESSAGE_QUEUE_BACKEND` 使用非法值时启动失败，不静默切换后端；
- 发送网络请求不持有数据库行锁；
- 死信和重试均有审计、状态和可操作错误。

#### 风险和回滚

当前只有 PostgreSQL 队列实现，回滚以暂停 Worker、保留投递任务和重新启动领取为边界，不删除事件或投递历史。未来新增其他后端时另立 ADR，不在本任务中设计跨系统事务。

### T06 HTTP API、权限与审计

#### 目标

提供符合现有 API、Scope/RBAC、错误和审计规约的通知服务接口。

#### 实施范围

- 渠道、模板、规则、投递查询和策略关联 API；
- 测试发送、预览、手动重试、死信查看和恢复 API；
- `notification:read/manage/test/retry` 权限和角色映射；
- 当前 Scope、继承共享和资源可见性校验；
- 敏感字段脱敏、请求体限制、稳定错误码、审计和速率限制；
- 旧巡检通知接口迁移到通知模块并删除重复业务实现。

#### 验收标准

- 每个 API 覆盖成功、参数错误、未认证、无权限、冲突、不可用和敏感字段场景；
- 普通用户看不到其他 Scope 的渠道配置和投递内容；
- 任何测试、重试、发布和渠道变更都能按 actor、Scope 和目标追溯；
- OpenAPI/类型客户端与后端字段一致。

#### 风险和回滚

权限扩大或旧路由双写会造成数据泄漏。先在服务层集中 Scope 校验，再切换路由；保留必要的数据库数据映射，不保留第二套写入口。

### T07 通知页面与菜单

#### 目标

交付可扫描、可操作且符合项目主题和可访问性规范的通知中心。

#### 实施范围

- 在权限菜单上方增加通知入口和页面装配；
- 在 `frontend/preview/notification-page-options-preview.html` 提供至少三种方案，等待用户确认；
- 实现渠道、模板、规则和投递四个区域/选项卡；
- 提供 provider 动态表单、密钥已配置状态、测试发送、模板预览、规则路由和策略关联；
- 覆盖 Scope 过滤、无权限、空数据、加载、失败、提交中、成功、重试和死信状态；
- 不在 `App.svelte` 放页面业务状态，页面专属请求归属于 notification feature。

#### 验收标准

- 预览先于实现，用户确认方案及取舍被记录；
- 桌面和窄屏无页面级横向溢出，键盘可完成核心流程；
- 主题令牌、图标、按钮、必填校验、错误提示和敏感字段显示符合前端规范；
- 页面不会把渠道、规则、模板混为不可解释的单一表单。

#### 风险和回滚

通知对象较多容易造成信息密度过高。以区域/选项卡隔离职责，保留投递详情抽屉；设计未确认前只交付预览，不直接冻结实现。

## 7. 需求级验收标准

1. 通知页面在权限菜单上方可见，并按 Scope、权限和当前组织范围过滤数据。
2. 渠道、模板、规则、投递记录职责清晰；巡检策略只关联规则，不复制规则和模板正文。
3. 依赖锁定版本公开的 provider 有可核验支持矩阵，渠道凭据加密保存且从不回传。
4. Finding 状态变化和通知事件在同一事务中提交；重复未变化异常不重复通知，恢复事件可追溯。
5. 模板版本不可变、变量受限、可预览，不能执行代码或访问未声明数据。
6. 规则支持事件、级别、目标、冷却、聚合、静默和多渠道路由；入队后使用规则/模板/渠道快照。
7. PostgreSQL 默认队列使用事务写入、`FOR UPDATE SKIP LOCKED`、租约、`LISTEN/NOTIFY` 和轮询兜底；不依赖 `pgmq` 或其他扩展。
8. `OPSK_MESSAGE_QUEUE_BACKEND` 默认值为 `postgres`，当前只接受该值，非法值启动失败。
9. 投递失败有有限重试、退避、死信和人工重试；投递历史和审计可查询且敏感信息已脱敏。
10. 后端、数据库、队列、前端和运维验证证据完整，未完成范围明确转移。
