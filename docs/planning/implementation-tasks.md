# OpsKeeper 分阶段实施任务书

## 1. 文档目的

本文将 OpsKeeper 的建设过程拆分为 15 个可独立审批、实施和验收的任务。任务按依赖关系顺序执行，后续任务默认依赖所有前置任务已经验收通过。身份、授权、管理与审计分别安排在 T03、T04、T05，避免将安全关键能力集中在一次实施和验收中。

本文只定义实施计划，不代表任何任务已经获得实施授权。

## 2. 执行与审批规则

1. 所有任务初始状态为 `待批准`。
2. 每个任务开始前，实施方需汇报目标、范围、关键决策、风险和预计文件变更，并取得用户明确批准。
3. 未获得当前任务批准时，不创建代码、不安装依赖、不执行数据库变更，也不提前实施后续任务。
4. 当前任务出现超出本文范围的设计变更时，暂停实施并重新申请批准。
5. 当前任务完成后，需提交变更摘要、验证命令、验证结果、遗留问题和下一任务说明。
6. 只有当前任务验收完成后，才申请下一个任务；批准一个任务不代表批准后续任务。
7. 文档修订不自动改变任何任务的审批状态。

状态定义：`待批准`、`实施中`、`待验收`、`已完成`、`阻塞`。

## 3. 目标工程结构

工程初始化后预计采用以下目录结构，实际创建须在任务 1 获批后进行：

```text
opskeeper/
├── backend/
│   ├── cmd/api/
│   ├── cmd/migrate/
│   ├── cmd/worker/
│   ├── cmd/scheduler/
│   ├── config/
│   ├── health/
│   ├── httpapi/
│   ├── migrations/
│   ├── organization/
│   ├── webui/
│   ├── database/       # 出现跨特性的连接生命周期需求时创建
│   ├── cache/          # 出现跨特性的缓存基础设施需求时创建
│   ├── connector/      # 外部平台协议形成稳定边界时创建
│   ├── messaging/      # 出现共享事件传输需求时创建
│   ├── version/
│   └── tests/
├── frontend/
│   ├── src/lib/
│   ├── src/routes/
│   └── tests/
├── deploy/
│   ├── Dockerfile
│   ├── compose/
│   └── helm/
├── docs/
└── Makefile
```

后端首版使用模块化单体并按业务特性建包。业务类型、Service、特性专属 Store 和测试留在同一特性包，通过文件划分职责；共享基础设施包只在出现真实的跨特性需求时创建，不预建空目录或全局 adapter 层。HTTP 作为协议边界独立，API、Worker、Scheduler 是独立运行单元。详细规则见 [Go 编码与工程组织通用规范](../standards/go-coding-conventions.md)。

## T01 工程初始化与质量基线

**状态：已完成**

验收记录：[T01 工程初始化与质量基线验收记录](../acceptance/t01.md)

### 目标

建立可重复启动、测试和检查的前后端分离工程，为后续业务功能提供稳定基础。本任务不实现任何组织、权限或资源业务。

### 实施细节

1. 初始化 Go Module，创建 `api`、`worker`、`scheduler` 三个入口及后端共享包。
2. 建立配置加载规范，支持环境变量和本地配置样例，禁止提交真实密钥。
3. 建立结构化日志、请求 ID、Recover、统一错误结构和 `/health/live`、`/health/ready`。
4. 初始化 Svelte 5、TypeScript、Vite，建立路由、API Client、基础布局和错误边界。
5. 在 `deploy/compose` 提供 PostgreSQL、Redis 本地环境及健康检查。
6. 提供 Makefile 命令，包括启动、格式化、静态检查、单元测试和数据库服务管理。
7. 增加 Go 和前端的最小单元测试，建立 `.editorconfig`、忽略规则和环境变量样例。
8. 固定主要依赖版本并记录本地开发前置条件。

### 预计文件范围

`backend/`、`frontend/`、`deploy/compose/`、`Makefile`、`.editorconfig`、`.gitignore`、配置样例和开发说明。

### 验收标准

- Go API、Worker、Scheduler 和 Svelte 开发服务均能启动。
- API 存活及就绪检查返回结构化结果。
- PostgreSQL 和 Redis 连通性能够进入就绪检查。
- 后端测试、前端测试、格式化和静态检查全部通过。
- 仓库中不存在真实凭据或与机器绑定的绝对配置。

### 不包含

数据库业务表、登录、RBAC、资源 CRUD、Kubernetes 接入和实际业务页面。

### 实施前待确认

- 当前目录不是有效 Git 工作区，本任务默认不初始化或修复 `.git`。
- 默认使用现有环境可支持的稳定 Go、Node.js 和包管理器版本，实施前报告实际检测结果。

## T02 PostgreSQL 与三级 Scope/组织模型

**状态：已完成，依赖 T01（已完成）**

验收记录：[T02 Scope 与组织模型验收记录](../acceptance/t02.md)

### 目标

实现统一 Scope 树以及平台、团队、项目组织模型，形成所有资源和权限的归属基础。

### 实施细节

1. 建立迁移框架和迁移执行命令，所有 Schema 变更可前滚和回滚。
2. 创建 `scopes`、`platforms`、`teams`、`projects` 表；组织状态只持久化在 Scope，组织表保存时间和软删除字段。
3. 使用数据库约束保证 Platform 无父节点、Team 父节点为 Platform、Project 父节点为 Team。
4. 建立团队编码平台内唯一、项目编码团队内唯一等索引。
5. 实现事务化 Store 和 Service，组织与 Scope 必须在同一事务创建或变更。
6. 提供团队和项目的创建、查询、修改、停用及分页 API。
7. 初始化单个平台根 Scope；不开放创建多个平台的业务接口。
8. 对父子关系、唯一性、软删除、并发创建和非法迁移编写集成测试。

### 预计文件范围

`backend/migrations/`、`backend/scope/`、`backend/organization/`、HTTP 路由、数据库测试工具。

### 验收标准

- 能创建团队和项目并得到正确的三层 Scope 路径。
- 非法父子层级、重复编码和孤立组织均被数据库或服务层拒绝。
- 停用上级组织时能阻止新建下级对象，并保留历史数据。
- 迁移在空数据库可重复执行，组织模块测试通过。

### 不包含

用户登录、角色授权、资源模型和前端管理页面。

## T03 本地身份与会话

**状态：已完成，依赖 T02**

验收记录：[T03 本地身份与会话验收记录](../acceptance/t03.md)

### 目标

建立可独立验收的本地身份和会话安全基线，不在本任务中引入角色授权复杂度。

### 实施细节

1. 创建用户、凭据和会话表，定义启用、停用、锁定和凭据轮换状态。
2. 通过 `make admin-create` 提供一次性初始化管理员流程；初始化凭据不得写入镜像、日志或仓库，bootstrap 不暴露为公开 HTTP 接口。
3. 使用 Argon2id 存储密码，并为参数升级和凭据轮换保留明确边界。
4. 实现登录、短期访问会话、刷新、注销和全部会话失效。
5. Cookie 使用 HttpOnly、Secure 和 SameSite 策略；浏览器使用 Cookie，非浏览器客户端可使用登录响应中的 Cookie 或 Bearer 访问令牌。
6. 提供只负责确认身份的认证中间件，保护业务 API 但不在本阶段实现角色授权判断。
7. 建立密码验证、会话轮换、重放、过期、注销、用户停用和并发刷新测试。

### 预计文件范围

身份与会话迁移、`backend/identity/`、HTTP 认证中间件、初始化命令和安全测试。

### 验收标准

- 可通过受控流程创建首个管理员，且没有默认生产密码。
- 用户可登录、刷新和注销，过期、被替换或失效会话不能继续访问。
- 用户停用后，其已有会话立即或在规定的最大时限内失效。
- 密码和会话令牌不以明文存储，不出现在日志和 API 响应中。
- 身份与会话测试覆盖正常、失败、重放和并发场景。

### 不包含

角色、权限、Scope 继承、用户管理页面和企业 OIDC/LDAP 单点登录。实施审批时可改为优先接入指定 SSO，但不得同时引入两套未经独立验收的身份流程。

## T04 三级 RBAC 与数据隔离

**状态：已完成，依赖 T03**

验收记录：[T04 三级 RBAC 与数据隔离验收记录](../acceptance/t04.md)

### 目标

实现内置角色、Scope 继承授权和服务端数据范围校验，保证任何访问路径都不会跨越有效授权范围。

### 实施细节

1. 创建角色、权限、角色权限和角色绑定表。
2. 内置 PlatformAdmin/Operator/Viewer、TeamAdmin/Operator/Viewer、ProjectAdmin/Operator/Viewer。
3. 提供 `Authorize(subject, permission, targetScope)` 授权服务和 HTTP 授权中间件。
4. 实现平台向团队/项目、团队向项目的权限继承，以及多个有效角色权限并集。
5. 定义组织与 Scope 状态对授权结果的影响，停用父级后不得继续使用后代权限。
6. 将 Scope 过滤注入查询层，按 ID 访问、列表、分页、计数和关联查询采用相同数据范围。
7. 建立角色矩阵、继承、跨团队隔离、直接对象访问和查询侧信道测试。

### 预计文件范围

授权迁移、`backend/authorization/`、各业务查询边界、HTTP 授权中间件和权限矩阵测试。

### 验收标准

- 平台、团队、项目三级角色按设计继承且不跨团队泄露。
- `resource:read`、`resource:use` 和管理权限能够独立判定。
- 通过对象 ID、列表、计数和关系查询均无法观察未授权数据。
- 停用或删除的 Scope 不再产生有效授权。
- 权限相关测试覆盖每个内置角色的正向和反向场景。

### 不包含

用户组、角色管理 API、自定义角色、权限缓存和 PostgreSQL RLS。

## T05 身份权限管理与安全审计

**状态：已完成，依赖 T04**

当前实施分支：`feat/t05-access-management-audit`

验收记录：[T05 身份权限管理与安全审计验收记录](../acceptance/t05.md)

### 目标

提供身份和角色绑定管理能力，防止授权人提升自身或他人到自身权限范围之外，并形成可追踪的安全审计记录。

### 实施细节

1. 创建用户组、组成员和必要的审计表，明确审计保留与敏感字段脱敏规则。
2. 提供用户、组成员和角色绑定管理 API。
3. 实现防越权授权：授权人不能授予自身不具备的权限或超出自身 Scope。
4. 实现权限缓存及精确失效；缓存故障不得扩大授权范围。
5. 记录登录、会话失效、用户状态变更、成员变更和角色绑定等安全事件；来源 IP 使用 API 可信代理边界解析后的客户端地址。
6. 建立并发角色变更、权限缓存失效、越权授权、审计完整性和敏感字段测试。

### 预计文件范围

身份管理与审计迁移、`backend/identity/`、`backend/authorization/`、管理 API、缓存边界和安全测试。

### 验收标准

- 管理员不能通过任何管理接口完成权限提升。
- 用户、组和角色绑定变更在规定时限内影响所有后续授权判断。
- 缓存不可用或数据过期时采用拒绝或权威存储校验，不沿用可能扩权的旧结果。
- 安全审计能够关联请求、操作者、有效角色、Scope、目标、结果和来源信息。
- 管理与审计测试覆盖正常、失败、并发和越权场景。

### 不包含

企业 OIDC/LDAP、自定义角色编辑器、细粒度显式拒绝策略和 PostgreSQL RLS。

## T06 统一资源目录、凭据和关系模型

**状态：已完成，依赖 T05**

当前实施分支：`feat/t06-resource-catalog`

### 目标

实现任意资源类型可归属平台、团队或项目的统一资源目录，以及符合 Scope 规则的资源关系。

### 实施细节

1. 创建资源、资源 Schema、凭据密文、资源关系、同步状态和 Scope 默认配置表。
2. 资源只引用 `scope_id`，由 Scope 节点确定平台、团队或项目层级。
3. 使用版本化 JSON Schema 校验不同 `kind` 的 `config`，首批注册架构设计中的资源类型。
4. Credential 资源保存元数据，密文使用信封加密接口存储；开发环境提供本地密钥实现。
5. 实现资源 CRUD、标签过滤、分页、连接状态和软删除。
6. 实现关系创建、查询和删除，严格校验“同 Scope 或向上引用”规则。
7. 使用递归 CTE 提供有限深度的上下游拓扑查询，并限制节点数量。
8. 实现显式默认解析规则：项目默认优先于团队默认，团队默认优先于平台默认。
9. 增加密钥脱敏、跨团队关系、非法向下依赖、循环和迁移影响测试。

### 预计文件范围

资源迁移、`backend/resource/`、`backend/credential/`、拓扑查询和相关 API。

### 验收标准

- 同一种资源可分别创建在平台、团队和项目 Scope。
- 项目能引用所属团队及平台资源，但不能引用其他项目或团队资源。
- API 永不返回凭据明文，日志中不出现敏感值。
- 拓扑查询遵守用户权限和最大深度限制。
- 资源移动 Scope 前能检测并拒绝失效关系。

### 不包含

具体资源连接器、Kubernetes 自动发现和资源管理前端。

## T07 Svelte 管理控制台基础功能

**状态：已完成，依赖 T06**

验收记录：[T07 Svelte 管理控制台基础功能验收记录](../acceptance/t07.md)

### 目标

提供可实际操作三级组织和资源模型的管理控制台，并正确体现当前作用域和用户权限。

### 实施细节

1. 实现登录、会话恢复、注销和未授权跳转。

- 不同角色只看到允许的导航和操作，后端拒绝伪造请求。

- 桌面和移动视口无内容重叠，关键端到端用例通过。

### 不包含

Kubernetes 导入向导、AI 对话和巡检页面。

## T08 Kubernetes 集群发现与项目导入

**状态：已完成，依赖 T07（已完成）**

验收记录：[T08 Kubernetes 集群发现与项目导入验收记录](../acceptance/t08.md)

### 目标

允许用户登记任意 Scope 的 Kubernetes 资源，预览 Namespace 和工作负载，并按集群作用域将 Namespace 映射为 Project、将工作负载映射为 Application。

### 实施细节

1. 将集群资源类型统一命名为 `Kubernetes`，保存非敏感连接配置并通过独立加密凭据关联 kubeconfig。
2. 使用 `client-go` 和 Kubernetes API 分页扫描 Namespace、Deployment、StatefulSet、DaemonSet、Job、CronJob、Pod、Service、Ingress 和 EndpointSlice。
3. 创建发现运行和发现项表；API 异步执行扫描，前端轮询进度并保留同步历史。
4. Namespace 只作为 Project 候选，用户可选择新建 Project、绑定已有 Project 或忽略；Namespace 本身不登记为资源。
5. 工作负载统一导入为项目级 `Application`，通过 `kubernetes.workload_kind` 保留 Deployment、StatefulSet、DaemonSet、Job 或 CronJob 类型；Pod 聚合为 `instances`，Service、Ingress 和 EndpointSlice 聚合为 Application 配置字段，均不登记为资源。
6. 平台级 Kubernetes 可映射到任意团队项目；团队级只能映射本团队项目；项目级只能映射当前项目。
7. 使用 `source_resource_id + external_uid + scope_id + kind` 形成幂等键，重复导入更新同一 Application；失联 Application 标记为 `unknown`。
8. 扫描只读取 Kubernetes 元数据和工作负载运行信息，禁止读取 Secret 内容。
9. 增加 `Repository` 和 `Artifact` 资源类型，并保持连接凭据与非敏感配置分离。
10. 保持 platform、team、project 三级 Scope；增加通用资源角色绑定，使 ProjectMember 可进入项目但只访问显式授权的具体资源。
11. 实现集群导入页、项目映射、Application 明细计数、资源角色管理和服务端隔离测试。

### 预计文件范围

发现迁移、`backend/discovery/`、资源级授权扩展、Kubernetes 客户端和前端导入/授权页面。

### 验收标准

- 三种 Scope 的 Kubernetes 资源都遵守各自导入边界。
- 用户确认前不创建项目或业务资源。
- 重复导入不产生重复 Application，失联工作负载变为 `unknown`。
- Namespace、Pod、Service、Ingress 和 Endpoint 不会出现在资源目录中。
- ProjectMember 只能看到显式绑定的资源，原有 Scope 角色仍可覆盖整个授权范围。
- 无权限、连接失败和大集群分页均有明确结果。

### 不包含

## 5. 任务审批记录模板

```text
任务：Txx 任务名称
当前状态：待批准
前置任务：已完成/不适用
本次范围：...
关键决策：...

风险与回滚：...
验证方式：...
需要用户确认：是否批准开始 Txx
```

```text
任务：Txx 任务名称
当前状态：待验收

验证命令与结果：...
偏离计划：无/...
遗留问题：无/...
下一步：申请验收；验收后再申请 Txx+1
```
