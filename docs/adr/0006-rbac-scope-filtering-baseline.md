# ADR-0006：T04 采用内置角色、向下继承和服务端 Scope 过滤

- 状态：已接受，T04 已完成
- 日期：2026-08-16

## 背景

T03 已完成身份确认，但组织 API 还没有授权判断。T04 需要在平台、团队、项目三级 Scope 上提供可解释的 RBAC 基线，同时保证列表、计数和按 ID 查询都不能绕过数据范围。用户组、角色管理 API、显式拒绝规则和权限缓存属于 T05 或后续任务。

## 决策

1. 使用 PlatformAdmin/Operator/Viewer、TeamAdmin/Operator/Viewer、ProjectAdmin/Operator/Viewer 九个内置角色；角色权限使用独立表保存，权限点采用 `domain:action` 名称。
2. 角色绑定只针对 T03 的本地用户，绑定一个明确的 Scope；用户组和组成员不在 T04 引入。
3. 绑定 Scope 的授权只向下覆盖自身及后代 Scope，不向上覆盖父 Scope；同一用户的多个有效绑定采用权限并集。
4. 只有用户状态为 `active`、绑定角色为有效内置角色且从绑定 Scope 到目标 Scope 的祖先链全部启用时，授权才成立。
5. API 认证中间件之后执行授权中间件。授权中间件计算服务端 Scope 过滤并写入请求上下文，组织 Store 必须在 SQL 的列表、计数、按 ID 和写入目标查询中应用该过滤。
6. T04 采用仅允许模型，没有显式拒绝规则；缺少授权返回 403，授权范围内不存在的对象返回 404，不把未授权对象加载到内存后再过滤。
7. 首个管理员通过受控 `make admin-create` 创建后获得 PlatformAdmin 绑定；该绑定由授权包的受控 bootstrap 操作幂等建立，不提供公开绑定 API。

## 后果

- 组织包不需要理解角色矩阵，只消费授权上下文中的允许 Scope 集合；不会建立全局 adapter/repository 层。
- 新增资源类型时必须复用同一个 Scope 过滤边界，不能复制一套独立的团队或项目判断。
- 当前授权查询以 PostgreSQL 为权威来源，暂不使用 Redis 缓存；T05 再评估缓存和精确失效。
- T04 不提供用户、角色和绑定管理接口；测试和受控 bootstrap 可建立绑定，管理能力由 T05 实现。
