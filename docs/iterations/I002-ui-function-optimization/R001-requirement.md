# I002-R001 控制台体验与高频工作流优化

**迭代：** I002-ui-function-optimization
**需求状态：** 实施中
**验收报告：** `R001-requirement-acceptance.md`

## 1. 需求背景

I001 已覆盖控制台的大部分平台能力，但当前前端将多个复杂工作流集中在单一页面中，页面反馈、列表检索、长任务恢复和窄屏使用体验仍不一致。用户需要在不同模块重复理解状态、手动确认刷新结果，异常时也缺少明确的下一步动作。

## 2. 目标

- 让用户在任意页面都能识别当前作用域、页面状态和下一步动作；
- 缩短概览到资源、诊断和待处理审批的路径；
- 让长任务断线、失败和重复提交有安全且可恢复的行为；
- 在不改变既有 API 安全边界的前提下，提升列表检索和表单操作效率；
- 通过自动化测试固定关键交互，降低后续迭代回归风险。

## 3. 范围

- 登录页面、应用壳、侧边导航、顶栏、作用域选择器和全局通知；
- 概览健康摘要、待处理事项和快捷入口；
- 组织/资源列表的搜索、筛选、状态提示和详情返回；
- 资源分类、按 Scope 可见性、类型专属添加、连接测试和详情展开；
- Kubernetes 发现预览与导入的选择、映射、进度和失败恢复；
- 诊断、巡检、通知和操作审批的执行状态、重试、取消/返回和结果查看；
- 桌面/窄屏响应式布局、键盘操作、语义标签和可见焦点；
- 单元、组件和 Playwright 端到端测试。

## 4. 非目标

- 不修改认证、RBAC、Scope 数据隔离、审计和受控操作审批规则；
- 不新增数据库迁移或外部连接器能力，除个人中心所需的 `0002_user_preferences` 用户字段迁移外；
- 不在本需求中实现 OI-006 的 Markdown Skill 编辑器和 Tool Catalog；
- 不以视觉改版为由删除现有功能或降低错误信息和审计信息的可见性。

## 6. 任务说明

### T01 登录页面优化

#### 目标

将现有登录页重构为现代、克制、直觉化的产品入口，并以确认方案的色彩、排版、间距、控件和反馈方式作为本轮后续页面的统一视觉基准。

#### 实施范围

- 桌面端采用大背景图与右侧登录区，左上角固定展示 OpsKeeper Logo 和平台名称；
- 使用真实或生成的运维基础设施位图，图像需清晰、可裁切且与 Kubernetes/运维场景直接相关；
- 登录区包含账号、密码、密码显隐、校验错误、提交 Loading、登录失败和服务状态；
- 不增加当前后端不支持的注册、找回密码或第三方登录入口；
- 窄屏改为顶部背景图、下方登录区，保留品牌首屏信号且无页面级横向滚动；
- 先评审以下五种方案，确认前不实施最终页面。

#### 固定设计约束

- 全局最多使用一种中性色和一种品牌高亮色，背景为纯白或 `#F8FAFC`，禁止渐变和装饰光斑；
- 右侧登录区是独立页面区域，不使用卡片套卡片或重阴影；
- 表单宽度控制在 `360-400px`，输入框提供示例 Placeholder，错误就地说明纠正方式；
- 页面进入后焦点落在账号输入框，Tab 顺序为账号、密码、密码显隐、登录按钮；
- 提交后按钮立即进入 Loading 并禁止重复提交，失败提示保留输入内容和重试入口；
- 背景图提供响应式裁切和深浅对比保护，Logo、名称与文字在所有视口清晰可读。

五种候选方案如下；用户已在评审中确认定稿方向。

#### 已确认设计

- 交互：账号/密码占位符、密码显隐、提交 Loading、禁用原因、错误提示、键盘焦点和移动端无横向溢出。

#### 验收标准

- 用户已从五种方案中确认一种，并记录选择理由与冻结的设计令牌；
- 桌面端满足“大背景图 + 右侧登录 + 左上角 Logo/名称”，窄屏完成对应重排；
- 登录成功、失败、字段非法、服务异常和提交中状态均有明确反馈；
- 键盘可完成全部登录操作，焦点清晰，错误可被辅助技术读取；
- 背景图片完成压缩与响应式加载，不阻塞表单首次可交互；
- Playwright 覆盖桌面、窄屏、成功登录、失败重试和重复提交保护。

#### 风险和回滚

背景图片可能影响首屏性能和文字对比度；实施时保留当前登录流程与 API 契约，只替换页面结构和样式。若视觉资源加载失败，页面降级为纯色背景且表单保持可用。

### T02 概览与作用域导航优化

#### 目标

让用户进入控制台后快速知道系统健康度、当前作用域和需要处理的事项。

#### 页面框架设计候选

T02 继承 T01 已确认的暖白表面、深灰文字和橙色操作色。以下方案只调整信息架构与布局，不引入新的主色；请先确认一种，再实施正式页面。

| 方案 | 桌面布局 | 信息层级 | 交互方式 | 适用取舍 |
|---|---|---|---|---|
| A 左侧导航 + 顶部上下文栏 | 240px 固定侧栏；顶部为面包屑、用户区；第二行独立放置作用域选择和刷新状态；主区为概览内容 | 导航、上下文、业务内容三层分明，健康状态置于主区首屏 | 侧栏切换页面；作用域选择后保留上下文栏并局部刷新；移动端侧栏折叠为顶部抽屉 | 最容易学习和扩展，适合高频运维工作；桌面端占用固定横向空间 |
| B 顶部导航 + 双栏工作区 | 顶部 64px 品牌与一级导航；主区左侧 280px 为作用域树和快捷入口，右侧为概览 | 当前作用域始终可见，概览内容拥有连续阅读宽度 | 作用域树支持键盘展开/收起；右侧卡片点击进入详情；移动端作用域树转为可展开抽屉 | 作用域感知最强，适合多团队协作；导航项较多时顶部会变拥挤 |
| C 窄侧栏 + 页面内分段导航 | 72px 图标侧栏；顶部只保留品牌、当前页面和用户；页面内使用分段 Tab 切换概览、资源、待处理事项 | 以当前任务为中心，减少长期可见的辅助信息 | 图标侧栏悬停显示名称；Tab 支持方向键；移动端侧栏转底部导航 | 视觉最轻、内容空间最大；图标识别和 Tooltip 质量要求较高 |
| D 上下文抽屉 + 沉浸式主区 | 64px 顶栏；左侧默认收起为 56px 图标轨；点击作用域按钮打开 320px 上下文抽屉；主区全宽 | 主区聚焦健康度和待处理事项，作用域按需出现 | 抽屉打开时保留主区滚动位置；点击遮罩或 Escape 关闭；移动端抽屉占全宽 | 最适合数据密集型概览和窄屏；作用域状态不如常驻布局直观 |

#### 已确认方案

2026-08-18，用户确认采用方案 A“左侧导航 + 顶部上下文栏”，并追加以下约束：

- 侧栏在右下角提供折叠图标；固定模式支持展开/仅图标两种状态，悬浮模式默认仅图标、鼠标移入展开；两种模式与折叠状态保存至当前用户的 `users` 表字段；
- 侧栏底部由“服务状态”替换为头像、用户名和右侧折叠图标；点击头像或用户名打开用户菜单，仅提供个人中心和退出登录；
- 个人中心可修改显示名、邮箱、电话和头像，头像仅接受最大 1 MiB 的 PNG/JPEG 并保存至 `users` 表；
- 个人中心集中配置自动、浅色、深色主题及侧栏行为；不设置独立的平台设置页；
- 当前领域模型没有用户与组织团队的归属关系，个人中心必须明确显示“所属团队未配置”，不得将当前作用域或可访问团队误报为所属团队。
- 标题栏右侧的工作区选择器仅面向非平台管理员显示：团队使用当前用户具备组织读取权限的可访问团队列表。默认选中接口返回的第一个团队；仅有一个团队时以不可点击文本展示，多个团队时提供切换菜单；项目使用下拉框切换当前团队内的项目。平台管理员不显示团队和项目选择器，并保持平台级上下文。
- 用户账户入口固定在侧栏左下角，显示头像、用户名和右侧折叠图标；用户菜单仅提供个人中心和退出登录，点击菜单外部区域自动关闭。侧栏折叠后，导航文本必须完全隐藏，展开后必须以 12px 字号左对齐完整展示。选中导航项的文字与图标使用同一橙色主色。

#### 共用框架约束

- 页面分为导航区、上下文区、主操作区和状态反馈区，区块间使用 8px 网格留白和浅色分割线；
- 每个页面只保留一个主操作，刷新、筛选、返回等使用次级或图标按钮；
- 首屏固定展示当前作用域、数据时间和健康状态；数据不可用时显示原因与重试入口；
- 桌面、768px 和 320px 视口均不得出现页面级横向滚动；移动端优先保证当前页面标题、作用域和主操作可见；
- 所有导航和抽屉支持 Tab、方向键、Enter、Escape，图标按钮提供 `aria-label` 与 Tooltip；
- 概览卡片只作为重复信息单元，不在页面区块内嵌套卡片；不使用渐变、重阴影或装饰性背景。

#### 实施范围

优化健康状态摘要、资源统计、巡检发现、待审批操作和最近诊断入口；作用域切换后明确展示继承关系、数据刷新状态和当前上下文。

#### 验收标准

- 首屏能区分健康、告警、未知和数据尚未加载；
- 概览中的待处理事项可直接进入对应详情视图；
- 切换作用域不会展示旧作用域数据，失败时给出重试入口；
- 桌面和窄屏首屏均无横向溢出。

#### 风险和回滚

概览聚合请求可能增加首屏等待；保留已有独立接口和降级展示，必要时回退为现有摘要布局。

### T03 团队与用户管理页面优化

#### 目标

让管理员在同一工作区内查看团队、团队成员、项目以及用户角色权限，并完成团队和用户创建。

#### 实施范围

采用“团队与用户”侧边栏父菜单及“团队管理、用户管理、角色管理”三个子菜单，每个子菜单进入对应的独立管理页面，同一时间聚焦一种管理对象。团队列表可展开成员和项目，用户列表展示直接及成员组继承的角色与权限；具备相应权限的管理员可新增、编辑、禁用团队和用户，并支持批量禁用。新增或编辑用户时可指定角色与 Scope，后端按 `member:grant` 可管理 Scope 过滤普通管理员可见用户，并阻止操作者授予自身不具备的权限。

#### 已确认方案

2026-08-19，用户先在五种可访问预览页面方案中选择方案 D，随后确认将页面内横向选项卡调整为侧边栏二级菜单。最终方案继承 T01/T02 的深色可收起侧栏、顶部上下文栏、暖白面板、低阴影和密集列表，并冻结以下页面结构：

- “团队与用户”作为侧边栏父菜单，“团队管理、用户管理、角色管理”作为三个子菜单；只有点击子菜单才进入并显示对应页面；
- 团队和用户选项卡标题区右侧分别放置新增与批量删除操作；
- 团队和用户每行提供编辑与删除操作，删除在现有领域模型中采用禁用语义并二次确认；
- 页面内容和操作按服务端 Scope 权限过滤，角色选择器只显示操作者可授予的角色；
- 页面继续使用深灰文字 `#2F2926`、橙色主操作 `#E7601B`、暖白表面 `#FFFFFF` 和背景辅助色 `#EEE8E5`。

#### 验收标准

- 团队以列表展示，每个团队可展开查看当前账号有权看到的用户和项目；
- 用户以列表展示角色和角色聚合后的权限，并支持按名称、用户名、邮箱或手机号搜索；
- 具备对应权限的管理员可新增、编辑、单个禁用和批量禁用团队或用户；新增用户可同时选择角色和授权 Scope；
- 非平台管理员只看到其具备 `member:grant` 权限 Scope 中关联的用户、角色绑定和成员组，只能执行其权限允许的操作；
- 用户只能授予其在目标 Scope 中完整持有权限的角色，前端筛选与服务端校验必须同时生效；
- 桌面与移动视口无横向溢出，弹窗表单具备明确标签、关闭入口和提交中状态。

#### 风险和回滚

现有模型没有用户直接归属团队关系，团队成员暂按团队 Scope 下的直接角色绑定与成员组成员聚合；后续若增加显式团队成员关系，页面数据源需迁移但交互结构保持不变。团队和用户删除采用禁用语义，保留关联数据和审计记录。

### T04 资源管理页面优化

#### 目标

让用户在一个按分类组织的资源工作区中，清楚识别资源所属的平台、团队或项目 Scope，并仅对自身可管理 Scope 的资源执行新增、编辑、删除和连接测试。资源添加流程必须根据类型显示受控且明确的专属字段，避免通用 JSON 配置成为日常操作入口。

#### 实施范围

- 资源按应用、中间件、数据库、制品库、代码库、Docker、Kubernetes、Skill、AI 模型和监控平台十类显示；MCP 作为 Docker、Kubernetes 的子类以及应用的受控接入方式呈现。资源目录固定为三级：一级为全部资源，二级为资源类型，三级为对应子类；支持搜索、分类筛选、状态筛选和可访问 Scope 筛选。AI 模型的统一入口、模型状态和专属创建流程在 T05 中单独优化；
- 根据当前账号的最高可见 Scope 显示资源：平台角色仅显示平台级资源；团队角色显示平台及当前团队级资源；项目角色显示平台、当前团队及当前项目级资源；每条资源显式标注资源 Scope；
- 用户可读取权限范围内的全部资源。上级 Scope 资源保留查看、展开详情和允许的使用入口，但隐藏或禁用编辑、删除等管理操作，并说明不可操作的原因；
- 资源列表行可展开显示连接地址或端点、标签、最近连接测试、能力摘要和关联信息；连接测试有进行中、成功、失败和重试反馈；
- 新增资源使用类型选择后的专属表单。应用只能从主机凭据、远程 Docker/Docker MCP 或 Kubernetes/Kubernetes MCP 三类受控来源之一获取；各中间件、数据库、制品库、代码库、Docker、Kubernetes、Skill 和监控平台显示其类型定义的连接和配置字段；AI 模型的模型厂商、大模型节点、能力交集、默认模型和发布总结由 T05 负责；
- 复用现有 API 的 Resource Schema、凭据隔离、Scope/RBAC 和审计边界。未有后端 Schema 的新资源类型先在设计中明确契约，实际接入前补充对应 API 与测试。

#### 六种候选方案

静态预览入口为 `frontend/public/t04-resource-design-preview.html`。六种方案均继承已确认的深色侧栏、暖白内容面、橙色主操作色、8px 圆角、低阴影、紧凑列表和浅色/深色主题令牌：

| 方案 | 核心结构 | 适用取舍 |
|---|---|---|
| A 分类工作台 | 顶部十类筛选器，列表内使用 Scope 徽标与行内展开 | 最快扫描；新增入口需要选择类型 |
| B Scope 时间线 | 按平台、团队、项目三段纵向分组，分类作为二级筛选 | Scope 继承最直观；跨分类比较较慢 |
| C 双栏资源目录 | 左侧三级资源目录（全部、类型、子类），右侧带搜索、状态和级别筛选的资源表与详情展开 | 类型和子类数量多时稳定；窄屏需保持目录可滚动 |
| D 类型画廊 | 十类资源以紧凑卡片作为入口，选中后显示该类列表 | 新增资源路径最清晰；大数据量时需要二次进入 |
| E 资源关系清单 | 分类表格与展开式详情面板并置，强调来源、连接与能力 | 适合连接测试和来源追溯；首屏信息密度高 |
| F 添加优先工作区 | 左侧资源列表、右侧类型专属添加/编辑表单，显示管理边界 | 适合持续录入；浏览空间较小 |

#### 验收标准

- 平台、团队和项目三种权限视角分别只展示所要求的 Scope 资源，且每条资源都能识别所属 Scope；
- 用户可查看其权限范围内的上级资源，但没有上级资源管理权时不可编辑或删除，并获得明确的只读原因；
- 十类资源及其子类都有稳定入口、空状态和添加入口；资源行按名称、分类、子类、平台和连接状态显示，类型专属表单不暴露凭据明文，应用来源仅可选择规定的三种受控来源；
- 资源连接测试、展开详情、加载、空数据、失败和重试状态可操作且可被辅助技术读取；
- 桌面、768px 和 320px 视口无页面级横向溢出；最终实现补充对应组件测试和 Playwright 场景。

#### 风险和回滚

现有资源 Schema 未必已覆盖十种分类及其专属字段。页面先保持现有 Resource Schema 和凭据 API 为唯一事实来源；新增类型只在后端契约、权限校验、凭据脱敏和测试完成后接入。若新布局出现 Scope 或管理操作判断偏差，回退到当前资源列表并保留服务端授权过滤。

### T05 AI 模型页面优化

#### 目标

以方案 B“健康摘要”为基础，提供现代化的 AI 模型列表和创建向导，让用户直观看到模型状态、模型连接状态和能力交集，并通过统一模型入口完成业务调用。

#### 实施范围

- 模型列表支持名称、级别和状态筛选，展示模型数量、能力交集、健康状态和是否默认；刷新状态直接在列表状态列反馈，不使用额外提示弹窗；
- 创建 AI 模型采用四步向导：基础信息、添加模型、路由策略、发布总结；基础信息支持图标选择、平台/团队/项目级别和默认模型设置；
- 模型表单支持内置模型厂商图标和地址预填、模型凭证显隐、温度、上下文窗口和能力卡片；模型只有通过真实连接测试后才加入列表，并显示实际错误原因；
- 模型能力由已添加模型的能力交集自动计算，不再设置单模态、多模态或独立的能力意图步骤；支持文本、视觉、音频、工具调用、结构化输出、流式输出、长上下文和深度思考；
- 平台、团队和项目级别分别最多一个默认模型，默认设置遵循对应级别管理员权限，并自动取消同级其他默认模型；
- 列表、向导、图标选择、连接状态、表单错误和发布总结完整适配浅色与深色主题。

#### 验收标准

- 模型列表可在桌面和窄屏查看，状态、级别、默认开关和模型能力均清晰可读；
- 添加模型时，必填字段错误就地标红，连接失败展示供应商返回的脱敏实际原因，未通过真实测试的模型不得进入列表；
- 发布总结完整显示基础信息、模型连接、能力交集、路由策略和发布前检查结果；
- 同一级别只能存在一个默认 AI 模型，非对应级别管理员不能设置或取消默认；
- 深浅主题下表单、步骤导航、状态标签、开关、下拉框和图标选择器均具备足够对比度，且无页面级横向溢出。

#### 风险和回滚

模型连接测试依赖外部 Provider 的协议和可用性；失败时保留实际错误原因并阻止发布。默认模型变更必须以服务端权限和唯一性校验为准；页面异常时可回退到只读模型列表，不影响既有资源目录。

### T06 AI 诊断页面优化

#### 目标

将 AI 诊断页面优化为类似 Codex、WorkBuddy 的 AI Agent 工作台。用户可以围绕目标资源发起可追踪的流式诊断对话，同时查看会话历史和可选择加载的上下文资源。

#### 交互要求

- 对话输入框支持文本输入；点击发送或按 Enter 发送，Shift + Enter 换行；输入框下方从左到右提供添加附件、添加链接、选择 Skills、选择 Agent、选择 AIEndpoint 和发送/停止按钮；AI 回复期间发送按钮变为停止按钮，点击后中断当前生成；
- 用户最后一条问题支持原地编辑并重新发送；AI 回复支持复制；回答因网络、服务或用户操作中断时，必须在回答末尾显示明确的中断原因；
- 页面显示会话历史，并支持加载已有会话；页面显示可加载为上下文的资源、变更和证据，每个来源提供独立开关决定是否加入当前诊断上下文；
- 诊断过程需要保留模型、Agent、Skill、上下文来源和中断状态等可审计元数据，不直接暴露凭据或未授权资源内容；
- 设计需同时适配浅色和深色主题，并在桌面与窄屏下保持输入、消息和上下文控制可用。

#### 设计产出

提供六种静态页面方案用于评审，文件为 `frontend/public/t06-ai-diagnosis-design-preview.html`；方案 F 已正式落地到前端诊断工作台，预览文件继续作为设计基准，不写入正式数据。

### T07 诊断巡检与审批工作流优化

#### 目标

使长任务和高风险操作的状态、结果及恢复路径清晰可控。

#### 实施范围

优化 SSE 诊断事件展示、断线后的状态恢复、巡检运行与发现查看、通知配置反馈，以及操作审批的风险提示、重复提交保护和结果/快照入口。

#### 验收标准

- 诊断连接断开后可恢复或明确失败，不重复创建会话；
- 巡检和操作请求展示进行中、成功、失败、拒绝和超时状态；
- 高风险操作在提交前显示目标、影响和审批状态，重复点击不会重复创建请求；
- 结果查看和返回路径不丢失当前作用域。

#### 风险和回滚

事件流时序和后端状态可能不一致；以服务端状态为准，前端只允许幂等刷新和安全重试，异常时回退到只读结果查看。

### T08 响应式与可访问性完善

#### 目标

保证常用控制台流程在窄屏和键盘操作下可完成。

#### 实施范围

检查 320px、768px 和桌面视口，修复横向溢出、固定宽度控件、表格和弹层布局；补充语义标题、表单标签、键盘焦点和状态播报。

#### 验收标准

- 关键页面在 320px 宽度下无页面级横向滚动；
- 所有核心操作可仅用键盘完成，焦点顺序和可见焦点合理；
- 表单控件具有关联标签，异步状态变化可被读取；
- 颜色对比和状态表达满足既有前端可访问性检查约束。

#### 风险和回滚

响应式规则可能引发桌面回归；采用视口矩阵截图和现有 E2E 流程逐页验证，问题可按页面回退。

### T09 自动化测试与性能验收

#### 目标

用可重复证据证明优化没有破坏既有能力，并控制首屏与交互开销。

#### 实施范围

补充 Svelte 单元测试和 Playwright 场景，覆盖登录、作用域切换、资源筛选、导入失败恢复、诊断断线、审批重复提交和窄屏布局；记录前端构建、检查和质量门禁结果。

#### 验收标准

- 新增场景在 CI 和本地可重复运行；
- `npm run check`、`npm run test`、`npm run build` 和 `npm run test:e2e` 通过；
- 关键视图没有新增明显的首屏阻塞或无界轮询；
- 验收报告记录命令、环境、结果和遗留问题。

#### 风险和回滚

E2E 依赖服务可能造成不稳定；测试数据和路由桩保持隔离，环境问题单独标记，不以跳过测试替代验收。

## 7. 需求级验收标准

1. 关键页面具备一致且可操作的加载、空数据、错误、重试和成功状态。
2. 概览、资源、发现、诊断、巡检和审批流程可在桌面与窄屏视口完成，且不改变权限与审计边界。
3. 长任务断线、失败、超时和重复提交均有安全的恢复或明确的只读降级路径。
4. 键盘、焦点、语义标签和状态播报通过对应自动化检查。
5. 前端检查、单元测试、构建和 Playwright 验收全部通过，并有可复核证据。
