# Go 编码与工程组织规范

## 1. 目的与适用范围

本文定义 OpsKeeper 后端的强制编码约束。新功能、重构和代码评审均应遵循本文；确需例外时，必须在变更说明中记录原因、影响范围和后续处理方式。

本项目采用 Go 模块化单体，默认使用 **Package by Feature（按业务特性组织）**。目标是让业务规则、持久化实现和测试保持在同一个高内聚包中，同时避免 Java 式分层目录、为假设需求提前抽象，以及以具体数据库或中间件污染业务命名。

本规范优先级如下：

1. 正确性、安全性和可验证性。
2. 清晰的业务所有权和单向依赖。
3. 简单、直接、符合 Go 习惯的实现。
4. 在已经出现真实变化点时再抽象。

## 2. 包组织原则

### 2.1 默认按业务特性建包

一个业务特性由一个顶层包拥有。例如组织能力由 `backend/organization` 负责，未来身份、授权、资源等能力分别由 `backend/identity`、`backend/authorization`、`backend/resource` 负责。

特性包内部按职责拆文件，不机械拆子包。`organization` 当前采用以下结构：

```text
backend/organization/
├── types.go
├── errors.go
├── service.go
├── validation.go
├── store.go
├── service_test.go
└── integration_test.go
```

这些文件仍属于同一个 `organization` 包：

- `types.go`：业务实体、值和输入类型。
- `errors.go`：对调用方稳定的业务错误。
- `service.go`：用例编排、业务校验和业务规则。
- `validation.go`：只供本特性使用的校验和规范化函数。
- `store.go`：service 所需的持久化能力接口、具体 store、SQL、事务、数据读取和驱动错误映射。
- `service_test.go`：不依赖外部服务的单元测试。
- `integration_test.go`：真实数据库、迁移和约束的集成测试。

文件名表达职责，不表达人为层级。文件不是封装边界；默认先将一个特性的 Store 放在单个 `store.go` 中，不按每个业务对象机械创建 `store_<object>.go`。只有文件已经明显影响导航和评审时，才按稳定能力边界拆文件。当同包文件能够保持清晰时，不应为了目录对称性增加包。

### 2.2 何时建立共享基础设施包

只有能力确实跨越业务特性或进程边界时，才建立独立基础设施包。允许的典型边界包括：

| 包 | 可以承担的职责 | 不应承担的职责 |
|---|---|---|
| `database` | 连接池创建、配置、生命周期和通用可用性检查 | 各业务表的 SQL、业务事务和错误语义 |
| `cache` | Redis 客户端生命周期、通用缓存原语 | 某个特性的缓存键和失效业务规则 |
| `messaging` | 事件传输、发布订阅生命周期和通用序列化约定 | 业务事件含义和业务流程编排 |
| `connector` | Kubernetes、Prometheus、Loki 等外部平台的协议客户端和能力注册 | 业务资源所有权、授权和用例规则 |

建立共享包至少满足一项条件：

1. 两个及以上特性已经出现相同的基础设施生命周期需求。
2. 第三方协议本身形成稳定、可独立测试的边界。
3. 该能力被 API、Worker、Scheduler 等多个进程共同使用。

不得只因未来“可能更换数据库”“可能复用”而创建 `adapter`、`common`、`utils`、`helpers`、`interfaces` 或 `implementations` 包。不得创建空包或只有占位注释的目录。

### 2.3 依赖方向

后端依赖应保持以下方向：

```text
cmd/*  ->  httpapi  ->  feature packages
  |                       |
  +-----------------------+
  |                       |
  +-> shared infrastructure packages
```

- `cmd/*` 是组合根，只负责读取配置、创建客户端、装配依赖、管理进程生命周期和处理退出信号。
- `httpapi` 负责 HTTP 协议，不拥有业务规则和 SQL。
- 特性包拥有业务规则以及该特性专属的持久化实现。
- 特性包不得导入 `cmd/*` 或 `httpapi`。
- 一个特性调用另一个特性时，只依赖调用方真正需要的小接口；出现循环依赖时应重新划分用例所有权，不得通过全局包绕开循环。

不要规定“所有模块必须通过接口互相调用”。只有测试替身、多个真实实现或稳定边界确实需要时才引入接口。进程内简单调用优先使用具体类型。

## 3. 命名规则

### 3.1 包和文件

- 包名使用简短、全小写、无下划线的单数业务名，如 `organization`、`resource`、`health`。
- 避免 `manager`、`processor`、`common` 等不能说明业务所有权的包名。
- 文件名使用小写下划线并按职责命名，如 `validation.go`、`service_test.go`。
- 特性包中的文件名不包含 `postgres`、`redis`、`kafka` 等具体产品名；实现细节由 import 和代码体现。
- 专门实现某个外部协议的 connector 包可以使用协议或产品名，例如 `connector/prometheus`，因为该产品就是包的稳定边界，而不是被泄漏到业务命名中的实现细节。

### 3.2 类型、接口和构造函数

- 导出名称必须表达业务概念，如 `Team`、`CreateProjectInput`、`Service`、`Store`。
- 不使用 `IStore`、`StoreInterface`、`ServiceImpl`、`RepositoryImpl`、`BaseStore`、`AdapterFactory`。
- 不在业务结构体名中加入具体数据库、缓存或消息中间件名称。
- 构造函数使用 `NewX`；包内只有一个主要类型且语义清楚时可使用 `New`。
- 避免包名重复，例如使用 `organization.Service`，而不是 `organization.OrganizationService`。
- 缩写保持一致，例如 `ID`、`URL`、`HTTP`、`API`，不写成 `Id`、`Url`。

### 3.3 可见性

- 默认不导出。只有被其他包合法使用的标识符才导出。
- 不为测试导出仅供包内使用的实现细节；同包测试或通过公开行为验证。
- 导出的类型和函数一旦形成跨包契约，修改时必须评估所有调用方。

## 4. 接口与依赖注入

### 4.1 接口由消费者定义

接口应靠近消费者，并只包含消费者实际调用的方法。当前 `organization.Store` 由 `Service` 消费，因此定义在 `organization` 包中，并允许 service 单元测试使用内存替身。

只有以下情况才引入接口：

1. 消费者需要隔离外部 I/O 进行快速单元测试。
2. 已存在至少两个真实实现。
3. 外部系统或进程边界需要稳定契约。

不得为每个结构体机械创建同名接口，不得为了“以后可能替换”预先添加工厂和接口层。

### 4.2 显式装配

依赖在 `cmd/*` 中通过普通 Go 代码显式创建：

```go
organizationStore := organization.NewStore(pool)
organizationService := organization.NewService(organizationStore)
handler := httpapi.NewRouter(logger, healthService, version, organizationService)
```

不使用依赖注入框架、全局 service locator、运行时反射装配或隐藏初始化的 `init` 函数。

构造函数必须验证无法在运行期恢复的结构性参数；正常业务错误由方法返回。构造完成的对象应立即可用。

## 5. 特性包职责

### 5.1 Service

Service 负责：

- 输入规范化和业务校验。
- 业务状态转换和跨多个 store 操作的用例编排。
- 返回对 HTTP、数据库和后台任务调用方一致的业务结果与错误。

Service 不负责：

- 解析 HTTP 请求或生成状态码。
- 拼接 SQL、处理数据库驱动错误。
- 读取进程环境变量。
- 记录密码、令牌、连接串或其他敏感数据。

当用例没有业务编排价值时，不强制增加空壳 Service；简单且稳定的能力可以直接由清晰的函数或具体类型提供。

### 5.2 Store

特性专属 Store 负责：

- SQL 查询和持久化数据转换。
- 该特性写操作的事务边界。
- 数据库约束错误到稳定业务错误的映射。
- 保持查询结果、软删除和 Scope 约束一致。

Store 不负责 HTTP、权限展示、配置文件读取或与本特性无关的通用连接生命周期。

SQL 和事务实现默认放在所属特性包内。只有两个以上特性确实共享同一种非业务存储原语时，才将该原语下沉到共享基础设施包；不得把各特性的 SQL 集中到全局 `adapter/postgres` 包。

### 5.3 HTTP

HTTP 层负责路由、请求体限制、JSON 解码、协议级校验、调用 service，以及业务错误到 HTTP 状态和错误码的映射。

- HTTP handler 依赖其实际使用的小接口。
- 请求结构体留在 `httpapi`；业务输入类型留在特性包。
- 不允许 handler 直接访问连接池或执行 SQL。
- 不为每个对象机械创建 DTO 和 Mapper。当 HTTP 契约与业务类型确实不同、安全上需要隐藏字段或版本兼容需要隔离时，再创建传输类型并显式转换。

## 6. Context、并发与资源生命周期

- 可能阻塞、调用外部系统或执行 I/O 的公开方法以 `context.Context` 作为第一个参数。
- 不把 Context 保存到结构体字段中，不传 `nil` Context。
- HTTP 请求链使用 `request.Context()`；后台任务创建有明确截止时间或可取消的 Context。
- 所有外部调用必须有超时或继承一个有截止时间的 Context。
- 启动 goroutine 必须明确所有者、停止机制和错误去向；禁止无法回收的后台 goroutine。
- 连接池、HTTP Client、Redis Client 等长生命周期资源在组合根创建并在进程退出时关闭。
- 对共享 map、缓存和可变状态明确同步策略；优先通过所有权减少锁，而不是依赖竞态检测补救设计。

## 7. 错误处理

- 任何可恢复失败都通过 `error` 返回，不使用 panic 表达业务错误。
- 使用 `%w` 增加操作上下文，例如 `fmt.Errorf("commit create team: %w", err)`。
- 使用 `errors.Is` 和 `errors.As` 判断错误，不比较错误字符串。
- 特性包只向调用方暴露稳定的业务错误，例如 `ErrNotFound`、`ErrConflict` 和 `ValidationError`。
- 数据库 SQLSTATE、驱动错误和第三方响应错误必须在边界处映射，不能直接决定 HTTP 状态码。
- 错误文本使用小写开头、无句号，并说明失败操作；对外响应不得泄漏 SQL、内部路径、凭据或第三方敏感详情。
- 忽略错误必须显式且有理由。清理路径可使用 `_ = resource.Close()` 或 `_ = tx.Rollback(ctx)`；业务路径不得静默丢弃错误。

## 8. 数据库与迁移

- 所有 SQL 使用参数绑定，不拼接用户输入。动态标识符必须来自受控白名单。
- 一个业务不变量涉及多次写入时，由拥有该用例的 Store 方法开启并提交事务。
- 事务尽量短，不在持有数据库锁时执行不受控的网络调用。
- 事务中所有查询必须使用同一个事务句柄；失败路径依赖延迟回滚，成功路径显式提交。
- 数据库约束是最终一致性防线，Service 校验不能替代唯一键、外键和检查约束。
- Schema 变更必须使用 `backend/migrations/sql` 中带前滚和回滚的版本化迁移；API 启动不得隐式执行迁移。
- 迁移使用受限的 `opskeeper` 业务数据库所有者，应用进程不得获得 `postgres` 超级用户凭据。
- 新 SQL 必须有覆盖关键约束、事务和错误映射的集成测试。

数据库初始化和迁移运行机制详见[本地开发环境](development.md)。

## 9. 配置、日志与安全

- 配置只在进程入口加载并以显式参数传递，不在业务包中重复读取环境变量。
- 环境变量统一使用 `OPSK_` 前缀；真实凭据不得提交到版本库。
- 使用结构化日志并提供稳定字段名；禁止拼接整段请求体或第三方响应作为日志。
- 密码、Cookie、Token、Authorization Header、数据库连接串、Credential 明文和加密密钥不得写入日志或错误响应。
- 记录标识符、动作、结果、耗时和可公开的错误分类，而不是敏感载荷。
- 对请求体、分页、并发、重试、响应体和外部调用设置上限。

## 10. 测试规范

### 10.1 测试归属

- 单元测试与被测代码同包或使用 `_test` 外部包，优先验证公开行为。
- Service 单元测试使用手写小替身，不引入大型 Mock 框架或自动生成的全局 Mock 层。
- Store 行为、SQL、事务、约束和迁移使用带 `integration` build tag 的真实 PostgreSQL 测试。
- HTTP 测试通过 `httptest` 验证状态码、响应结构、错误映射和请求限制。
- 修复缺陷时必须先确定可稳定复现缺陷的测试层级，并增加回归测试。

### 10.2 测试质量

- 测试名称描述行为和条件，不按实现函数逐行镜像。
- 测试相互隔离、可重复运行，不依赖执行顺序和生产数据。
- 时间、随机值和并发测试必须避免无界等待和脆弱 sleep。
- 集成测试创建临时 Schema 或等价隔离空间，并在结束时清理。
- 测试断言应包含实际值和期望语义，便于定位失败。

提交前至少执行：

```bash
make quality
git diff --check
```

修改 Store、迁移或数据库约束时还必须运行：

```bash
OPSK_TEST_DATABASE_URL='postgres://opskeeper:opskeeper@localhost:5432/opskeeper?sslmode=disable' \
  make backend-integration-test
```

## 11. 文件和包的拆分时机

默认先使用职责清晰的少量文件，不为每个对象或方法创建文件。出现以下信号时才应在同一特性包中按稳定能力拆文件：

- 一个文件同时承担业务校验、SQL、HTTP 和数据转换等多个职责。
- 团队、项目等能力可以形成清晰的文件边界。
- 文件增长导致代码评审难以定位变更。

只有出现以下信号时才考虑拆包：

- 子能力有独立且稳定的公共 API，并被多个调用方复用。
- 子能力具有独立生命周期、协议或安全边界。
- 当前包出现无法通过拆文件解决的循环依赖或所有权混乱。

拆包不得只是为了减少行数。新包必须能用一句话说明唯一职责，且不能依赖父包的内部细节。

## 12. 明确禁止的模式

- 按技术层创建全局 `models/`、`services/`、`repositories/` 并把所有业务混放其中。
- 为每个特性在全局 `adapter/postgres` 下建立平行实现。
- `ServiceImpl`、`RepositoryImpl`、`BaseStore`、通用 CRUD 基类和泛型工厂。
- 没有实际消费者的接口、只有一个简单调用的包装层、仅转发参数的 Mapper。
- `common`、`utils`、`helpers` 作为无所有权代码的收容目录。
- 通过包级可变全局变量、`init` 副作用或 service locator 隐式传递依赖。
- 在 HTTP handler 中执行 SQL，或在 Store 中生成 HTTP 响应。
- 为尚不存在的数据库、中间件或部署方式提前设计通用适配层。

## 13. 新特性评审清单

提交新特性或大规模重构前，逐项确认：

- [ ] 包名表达业务所有权，而不是技术层或模糊职责。
- [ ] 业务代码、HTTP 和共享基础设施的依赖方向单向且无循环。
- [ ] 接口由真实消费者定义，方法集合没有为未来需求扩张。
- [ ] 类型、接口、文件名未泄漏可替换的数据库或中间件名称。
- [ ] 业务规则位于 Service，SQL 和事务位于所属特性的 Store。
- [ ] 事务覆盖完整业务不变量，数据库约束提供最终防线。
- [ ] 错误已在边界映射，调用方不依赖驱动错误或错误字符串。
- [ ] Context、超时、资源关闭和 goroutine 生命周期明确。
- [ ] 日志和错误响应不包含凭据或敏感载荷。
- [ ] 单元、HTTP 和集成测试与变更风险相匹配。
- [ ] 没有为假设变化点增加 adapter、factory、DTO 或通用工具包。
- [ ] `make quality`、相关集成测试和 `git diff --check` 通过。

## 14. 例外处理

本规范不是禁止合理演进。若 Ports and Adapters、独立 adapter 包或更严格分层在某个边界确有价值，变更必须同时证明：

1. 已存在多个真实实现、独立协议边界或明确的发布边界。
2. 新抽象降低了当前复杂度，而不是只转移文件位置。
3. 依赖方向、测试策略和迁移成本已经说明。
4. 架构文档和本规范中的相关示例同步更新。

未经上述论证，默认继续使用按业务特性组织的简洁结构。
