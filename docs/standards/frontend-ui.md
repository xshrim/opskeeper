# 前端 UI 与交互规范

本文是 OpsKeeper 前端页面设计、实现和评审的强制性规范，适用于 `frontend/` 下的所有页面、组件和交互。规范的核心目标是：**极致简洁、结构清晰、交互明确、体验友好**。拒绝无意义的装饰，追求零学习成本的直觉化操作。

## 1. 整体视觉与布局

### 1.1 色彩与全局主题令牌（强制）

- 浅色主题以 `#E7601B` 为主题轴，使用暖白、橙色和中性灰；深色主题以 `#173C35` 为主题轴，使用 `main` 分支一致的暖深色表面和 `#18A27D` 主操作按钮。
- 两套主题严格隔离：浅色主题不得使用深色主题的深绿值，深色主题不得将浅色主题的橙色作为主题轴或普通背景。
- 背景必须使用当前主题令牌：两套主题均使用各自的低干扰表面值；不得新增第三套背景主题或跨主题覆盖令牌。
- 禁止复杂渐变背景和高对比度的杂色组合；状态颜色只用于表达状态，不作为装饰。

项目只维护两套全局主题，不允许页面或组件维护局部主题：

- 浅色主题以 `#E7601B` 为唯一主轴，使用暖白、橙色和中性灰；禁止使用青绿色作为浅色主题的交互、选中、背景或装饰色。
- 深色主题以 `#173C35` 为唯一主题轴，主操作按钮单独使用 `#18A27D`；其页面、表面、输入框和边界取值与 `main` 分支一致，状态色仅按成功、警告、错误语义使用。
- 新增元素必须使用 `var(--theme-*)` 令牌或公共主题类，禁止直接写十六进制颜色。组件可以定义仅用于语义映射的别名，但别名必须直接引用全局令牌，不得存储独立颜色值。
- 普通面板、列表和卡片必须使用 `--theme-border`；深色主题该令牌为 `#473E39`，浅色主题保持原有暖灰 `#EADFD9`。横向分割线使用独立的 `.theme-divider`，其 `--theme-divider` 与 `--theme-border` 保持一致。只有输入框、下拉框和按钮可以使用更强的控件边框，聚焦时使用主题轴色。
- 组件必须同时定义普通、悬停、焦点、选中、禁用、成功、警告和错误状态；状态颜色不能只依赖颜色本身，还要有文字、图标或边框辅助表达。

全局令牌定义在 `frontend/src/app.css`，公共控件类包括：

```text
.theme-surface       普通表面
.theme-raised        抬升表面
.theme-control       输入框/下拉框等控件
.theme-interactive   可悬停和可聚焦的交互元素
.theme-selected      选中状态
.theme-status-success / warning / danger
.theme-divider       横向分割线
```

#### 公共控件样式契约

公共控件必须建立在上述令牌之上，页面只组合语义类，不复制颜色值。下表是所有页面必须遵守的基础状态矩阵：

| 控件/状态 | 前景 | 背景 | 边框/焦点 |
| --- | --- | --- | --- |
| 普通按钮/图标按钮 | `--theme-fg-muted` | 透明 | 透明 |
| 按钮悬停 | `--theme-accent` | `--theme-bg-hover` | `--theme-border-focus` |
| 主按钮 | `--theme-accent-contrast` | `--theme-action` | `--theme-action` |
| 主按钮悬停/按下 | `--theme-accent-contrast` | `--theme-action-hover` / `--theme-action-active` | 同背景 |
| 输入框/下拉框 | `--theme-fg` | `--theme-bg-input` | `--theme-border-strong` |
| 输入框悬停 | `--theme-fg` | `--theme-bg-hover` | `--theme-border-strong` |
| 输入框聚焦 | `--theme-fg` | `--theme-bg-input` | `--theme-border-focus` + `--theme-focus` 焦点环 |
| 选中项/选中标签 | `--theme-teal` | `--theme-bg-selected` | `--theme-teal` |
| 禁用控件 | `--theme-fg-disabled` | `--theme-bg-subtle` | `--theme-border` |
| 成功/警告/错误状态 | 对应 `--theme-success/warning/danger` | 对应 `--theme-bg-*-soft` | 可选对应颜色边框 |

推荐的公共组合类已经在 `frontend/src/app.css` 实现：

```html
<section class="theme-surface">普通面板</section>
<div class="theme-raised">浮层或抬升面板</div>
<input class="theme-control" />
<button class="theme-interactive">次级操作</button>
<button class="theme-interactive theme-selected">当前选项</button>
<span class="theme-status-success">正常</span>
```

控件还必须满足以下尺寸和交互约束：最小点击区域 32px；圆角通常为 4-8px；边框为 1px；过渡时间 120-180ms；键盘焦点不可隐藏；纯图标按钮提供 `aria-label` 和 Tooltip；加载、禁用、错误状态不能只依赖颜色表达。新增控件若需要特殊色彩，应先扩展全局令牌和本节状态矩阵，再在页面使用。

主题审计规则：实际颜色值只能出现在 `frontend/src/app.css` 的全局令牌定义区；页面、组件和组件级覆盖不得直接写 HEX、RGB 或 RGBA 颜色。公共控件的覆盖范围包括普通/主/危险按钮、图标按钮、文本按钮、单行输入框、多行文本框、下拉框及其选项、复选框、开关、分段控件、Tooltip、弹窗遮罩、加载指示器和状态徽标。每个控件必须复用本节令牌，并覆盖悬停、焦点、选中、禁用和状态反馈；不再使用局部主题令牌或 `!important` 强行压过全局主题。

### 1.2 视觉层级

- 页面必须划分为明确的功能区块，例如顶部导航、主操作区、侧边辅助区和底部状态栏。
- 区域之间使用 8px 网格倍数留白（如 `16px`、`24px`、`32px`）或 `--theme-border` 分割线区分，避免拥挤。
- 卡片和容器禁止重阴影，优先使用 1px 细边框或微弱柔和的阴影，例如 `0 1px 3px rgba(0, 0, 0, 0.05)`。
- 页面结构优先使用清晰的栅格和对齐关系，不使用装饰性容器堆叠信息。

### 1.3 排版

| 层级 | 字号/字重 | 用途 |
|---|---|---|
| 标题 | `18-20px` / Bold | 页面和主要区块标题 |
| 副标题/区域头 | `14-16px` / Medium | 次级区块标题 |
| 正文 | `14px` / Regular | 主要内容和表单文字 |
| 辅助/提示 | `12px` / Regular | 说明、状态和辅助信息 |

正文和长文本行高固定在 `1.5-1.6`，避免因内容长度变化造成布局跳动或难以阅读。

## 2. 表单与输入交互

### 2.1 占位符与说明

- 所有输入框必须提供清晰的 `placeholder`，提示格式或典型示例，例如“例如：`example@domain.com`”或“请输入 1-100 之间的整数”；不能只提供空输入框。
- 复杂或易混淆的字段必须在标签旁提供问号图标和 Tooltip，悬停或聚焦时展示用途、格式和示例。
- Label 必须与对应控件关联；不能只用 placeholder 代替标签。

### 2.2 防错与实时校验

- 校验应在输入或失焦时及时触发，错误信息直接显示在对应输入框下方，使用高亮红色（如 `#EF4444`）。
- 错误提示必须明确说明如何纠正，不能只显示“格式错误”或“无效输入”。
- 数字、电话、日期等特定输入优先使用限制性控件（数字输入框、日期选择器）或输入屏蔽，从源头减少无效输入。
- 提交前保留完整校验；服务端校验失败时，将错误定位回对应字段或表单区域。

## 3. 操作反馈与状态感知

### 3.1 操作层级

- 每个页面或功能区只保留一个最突出的主按钮（Primary Button）。其他操作使用次级按钮或文本按钮，避免多个高亮按钮争夺焦点。
- 条件不满足时，主操作按钮必须呈明确禁用状态；悬停或聚焦时通过 Tooltip 告知原因，例如“请先填写必填项”。对于原生禁用控件，Tooltip 应绑定到可获得悬停事件的外层元素。
- 不熟悉的纯图标按钮必须提供 Tooltip；删除、保存、刷新、缩放等通用符号可使用图标按钮，但仍须具备可访问名称。
- 图标统一使用 `lucide-svelte`，优先按需引入对应图标组件；禁止在按钮中混用文字、Emoji 或手绘 SVG 作为同类操作的替代图标。纯图标按钮必须同时提供 `aria-label` 和 Tooltip。

### 3.2 加载与结果

- 任何耗时操作（异步请求、提交表单、导入、诊断或审批）必须立即反馈：按钮切换为 Loading 状态，或在内容区域展示 Skeleton/进度状态。禁止界面静止无响应。
- 成功操作使用轻量 Toast，显示绿色提示并在 2-3 秒后自动消失。
- 失败操作使用红色提示，并保留手动确认、重试或返回入口；错误信息必须说明下一步动作。
- 操作期间禁止重复提交；完成后应同步更新相关列表、详情和状态，不要求用户盲目刷新。

### 3.3 破坏性操作

删除、覆盖、重置等不可逆操作必须弹出 Modal 二次确认，明确说明后果，例如“删除后数据不可恢复，确定继续吗？”。确认按钮应使用明确的破坏性语义，取消操作应始终可见。

## 4. 空状态与异常处理

### 4.1 空状态

列表或图表无数据时，不得留白或只显示“暂无数据”。必须展示简约的图标/插画、一句简短说明以及下一步引导按钮，例如“暂无任务，点击下方按钮创建第一个任务”。

空状态应区分“尚未创建”“筛选无结果”和“暂无权限”，并提供对应的清除筛选、创建或申请权限入口。

### 4.2 网络与系统错误

页面加载失败时，必须提供清晰的错误提示和一键“刷新/重试”入口。错误状态不能覆盖原有页面上下文，用户重试后应保留作用域、筛选条件和已填写但未提交的内容（涉及敏感信息时遵循安全策略）。

## 5. 响应式与可访问性

- 所有可点击元素（按钮、卡片、列表项、链接）必须包含明确的 Hover 和 Active 视觉变化，例如轻微变深、背景变化或指针变为 `pointer`。
- 支持 Tab 键顺畅切换输入焦点；当前 Focus 元素必须有清晰可见的焦点样式，不能仅依赖鼠标操作。
- 核心流程必须可以仅使用键盘完成，焦点顺序应符合页面阅读和操作顺序。
- 控件、状态和异步变化应提供语义标签、可访问名称和必要的状态播报；不能只依赖颜色、图标或位置表达含义。
- 布局必须适配桌面和窄屏视口，内容、按钮和文字不得重叠或产生页面级横向溢出。

## 6. 实施与验收

- 新增或修改页面时，需求和验收记录必须覆盖加载、空数据、错误、禁用、提交中、成功和失败状态。
- UI 评审至少检查桌面与窄屏视口、鼠标与键盘操作、表单校验、重复提交保护和破坏性操作确认。
- 关键交互应通过 Svelte 单元/组件测试或 Playwright 场景固定；视觉变化不能替代行为验收。
- 若现有页面暂时无法满足本规范，必须在对应迭代需求中明确差距、改进任务和验收标准。

### 6.1 前端模块拆分规范

- `App.svelte` 只负责应用级装配、路由/菜单切换、全局布局和跨页面共享状态；不得承载任一菜单页面的完整模板、页面状态或页面业务函数。
- 每个菜单页面必须拥有一个页面级主文件：`frontend/src/features/<feature>/<Feature>Page.svelte`。该文件收敛该页面的变量、派生状态、事件处理、数据加载、页面模板和页面专属组件组合。
- 页面目录默认只保留一个页面级 `*.svelte` 文件。只有以下情况可以新增 Svelte 文件：独立选项卡、弹窗/抽屉、需要独立焦点与生命周期的交互区域，或跨页面复用的通用组件。标题栏、工具栏、字段组、列表行、状态块和步骤导航不得仅因模板较长而拆成组件。
- 页面内的弹窗、选项卡和抽屉必须放在对应页面目录，并由页面主文件控制其打开状态和数据流；不得把页面状态拆散到多个碎片组件中。
- 页面专属辅助函数、类型和状态优先放在页面目录；跨页面的数据访问和纯函数才放在 `frontend/src/lib/`。跨页面复用的布局放在 `frontend/src/layouts/`，通用交互控件放在 `frontend/src/components/`。
- 页面主文件与弹窗/选项卡之间通过明确 Props、事件回调或 Store 通信；子组件不得直接修改页面外部状态。除真正独立的交互区域外，避免多层 Props 转发和为字段绑定创建包装组件。
- 样式按页面作用域归属组织：全局主题令牌和基础控件保留在 `app.css`，页面专属样式放在 `frontend/src/features/<feature>/<feature>.css`，并继续使用全局 `--theme-*` 令牌，不得复制颜色值或建立局部主题。
- 拆分或合并必须保持现有 DOM 语义、可访问属性、键盘路径、状态反馈、主题令牌和 CSS 类名；迁移后删除原实现和无用组件，禁止并行保留重复模板。
- 页面重构采用渐进迁移：先建立页面主文件并迁移完整模板，再将页面状态和业务函数收敛到该文件，最后仅保留必要的弹窗、选项卡和跨页面组件。每步完成必须通过 `npm run check`、相关测试和生产构建。

## 7. 持续设计与方案评审约束

- 前端页面必须逐页重新设计和评审；不得以一次性全局改版替代对单个页面信息架构、操作路径和状态反馈的具体设计。
- 每次提交一个页面的设计方案时，至少提供三种有实质差异的风格与布局方案供选择。每种方案必须说明视觉语言、信息层级、主要操作位置、核心交互方式、响应式表现和可访问性影响，并列出适用场景与取舍。
- 设计方案必须以可访问的预览页面交付，不得以静态截图代替预览页面。预览页面应支持候选方案切换，并真实呈现核心布局、主要交互和权限状态；截图仅可作为评审记录的补充材料，不得作为方案交付物。
- 未经用户确认，不得将某个方案视为最终设计或直接以该方案完成页面实现。确认结果必须记录在对应迭代/需求或页面设计记录中。
- 一旦前面的页面样式和布局被确认，后续页面必须继承已确认的设计令牌和模式，包括色彩、字体、间距、圆角、边框、阴影、控件状态、导航结构和反馈方式；除非提出新的方案并重新获得确认，不得另起一套视觉风格。
- 在整体风格已经统一的前提下，后续每个页面仍需提供三种以上符合本规范的排版布局和交互方式供选择。候选方案可以调整信息分组、密度、导航路径和操作编排，但不得破坏已冻结的视觉令牌、可访问性和状态反馈规则。
- 方案比较应优先围绕用户任务完成效率、信息可扫描性、错误恢复和窄屏可用性，不得以装饰数量、视觉复杂度或实现炫技作为主要评价标准。
- 已确认的方案、未采用方案及选择理由应保留简短记录，作为后续页面设计和迭代验收的依据，避免反复讨论已经确定的决策。
