# ADR-0008：T06 使用统一资源目录、Scope 关系约束和密文凭据边界

- 状态：已接受，T06 已完成
- 日期：2026-08-16

## 背景

OpsKeeper 后续需要统一管理 Kubernetes、业务应用、中间件、可观测平台和 AI 能力资源。资源类型不断扩展，不能为每一种资源设计独立的组织外键，也不能让资源关系依赖前端或连接器自行保证 Scope 安全。外部系统凭据还必须与登录用户凭据分离，API 和日志不能暴露密文或明文。

## 决策

1. 所有资源只通过 `scope_id` 表达平台、团队或项目归属，类型由 `kind` 标识，类型特有配置放在 JSONB 中，并记录实际使用的版本化 Schema。
2. 首批资源 Schema 注册在 PostgreSQL `resource_schemas` 中；服务端在创建和更新资源前校验对象类型、必填字段、属性类型和额外属性规则。
3. 外部系统凭据单独存放在 `resource_credentials`。API 只返回凭据元数据，密文通过 `Encryptor` 接口写入；开发环境使用本地 AES-GCM 实现，生产环境必须显式提供 `OPSK_CREDENTIAL_KEY`。
4. 关系只允许同 Scope 或向上引用：项目可引用所属团队和平台资源，团队可引用平台资源，上级 Scope 不得依赖下级资源。数据库触发器和服务层共同校验，并通过递归查询拒绝环路。
5. 资源拓扑使用 PostgreSQL 递归 CTE，服务端固定最大深度和节点数量，并在查询结果上继续执行当前用户的资源可见范围过滤。
6. 默认配置按请求 Scope 向上解析，项目优先于团队、团队优先于平台；默认资源必须位于请求 Scope 可见的祖先链上。

## 后果

- 新资源类型只需注册 Schema 和后续连接器，不需要修改组织模型或新增多态外键。
- 数据库约束可以阻止绕过 HTTP API 的非法关系、环路、无效 Scope 移动和跨 Scope 凭据引用。
- 资源查询允许项目读取所属团队和平台资源，但修改、删除、关系管理和凭据管理仍要求当前授权 Scope 精确匹配。
- T06 不实现具体连接器、Kubernetes 自动发现、资源管理前端和资源连接测试；这些能力由 T08、T09 及后续任务交付。
