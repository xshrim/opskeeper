# Go 编码与工程组织通用规范

## 1. 目的与适用范围

本文定义 Go 应用项目通用的编码和工程组织约束，适用于新功能、重构、代码评审和持续集成。具体项目可以补充目录、配置、数据库和发布约定，但不应在通用规范中写入业务名称、固定仓库路径、账号、端口或中间件凭据。

规范中的关键词含义如下：

- **必须**：除非经过明确的例外评审，否则不得违反。
- **应该**：默认做法；偏离时需要有清晰理由。
- **可以**：根据实际复杂度选择，不要求机械应用。

规则优先级如下：

1. 正确性、安全性和可验证性。
2. 清晰的所有权和单向依赖。
3. 简单、直接、符合 Go 习惯的实现。
4. 在真实变化点出现后再抽象。

## 2. 基本原则

### 2.1 保持简单

- 优先使用标准库和普通 Go 代码解决问题。
- 优先使用 Go 新版本中提供的更简洁或性能更好的写法，但不要降低可读性。
- 不为假设中的复用、替换或扩展提前建立抽象层。
- 不通过框架隐藏对象创建、依赖关系、错误传播或生命周期。
- 重复少量清晰代码通常优于过早引入难以理解的通用机制。
- 抽象必须降低当前复杂度，而不是只改变文件位置或名称。

### 2.2 高内聚、低耦合

- 一个包应该拥有一组关系紧密的概念和行为。
- 业务规则、数据所有权和测试应靠近所属功能。
- 包的公开 API 应尽可能小，内部实现默认不导出。
- 依赖方向必须明确；禁止通过全局变量或无所有权的公共包形成隐式耦合。

### 2.3 组合优于继承式设计

- 使用小结构体、小接口和显式组合。
- 不模拟类继承、抽象基类或通用 CRUD 基类。
- 只有存在真实消费者时才定义接口。
- 通过构造函数注入依赖，不使用 service locator 或运行时反射装配。

## 3. Module 与仓库组织

### 3.1 Module 边界

- 一个可独立版本化和发布的 Go 组件应该拥有独立 `go.mod`。
- 不因为目录较多就拆分 Module；只有版本、依赖或发布边界确实独立时才拆分。
- Module Path 必须与预期使用方式一致。公共 Module 使用可获取的代码托管路径；仅仓库内使用的 Module 可以采用项目约定的本地命名空间。
- 多 Module 仓库必须明确各 Module 的所有权、依赖方向和统一验证命令。
- Go 应用与前端、部署配置等共处一个 Monorepo 是可行的，各工程应保持独立依赖清单和构建入口。

### 3.2 `internal` 的使用

`internal` 是 Go 工具链提供的导入边界，不是必须采用的目录层级。

- 需要由编译器阻止仓库外部或父目录外部导入时，可以使用 `internal`。
- 应用代码本来就只在单一 Module 内使用，且不需要额外边界时，可以直接放在 Module 根下的业务包中。
- 不得为了“看起来标准”而机械增加 `internal`，也不得为了缩短路径而移除确实需要的封装边界。

### 3.3 可执行程序

- 可执行程序入口放在 `cmd/<program>`。
- `main` 包只负责配置加载、依赖创建、进程生命周期、信号处理和启动。
- 业务规则、协议实现和数据访问不得堆积在 `main.go`。
- 多个可执行程序共享业务包和基础设施包，不通过复制代码形成独立实现。

## 4. 包组织

### 4.1 默认按业务功能组织

应用代码默认采用 **Package by Feature**：包名表达业务能力或稳定技术能力，而不是全局技术层。

一个典型功能包可以从以下最小结构开始：

```text
feature/
├── types.go
├── errors.go
├── service.go
├── validation.go
├── store.go
├── service_test.go
└── integration_test.go
```

这些文件的常见职责是：

- `types.go`：实体、值对象和用例输入输出。
- `errors.go`：对调用方稳定的业务错误。
- `service.go`：用例编排和业务规则。
- `validation.go`：该功能内部的校验与规范化。
- `store.go`：持久化契约和实现。
- `service_test.go`：快速、无外部依赖的单元测试。
- `integration_test.go`：真实外部依赖参与的集成测试。

这只是渐进式模板，不要求每个包具备所有文件。没有业务编排时可以没有 Service，没有持久化时可以没有 Store，没有独立错误语义时可以不创建 `errors.go`。

### 4.2 何时建立共享基础设施包

跨功能复用且具有稳定技术边界的能力可以建立独立包，例如：

| 包类型 | 适合承担的职责 | 不应承担的职责 |
|---|---|---|
| 数据库基础设施 | 连接创建、配置、生命周期、通用可用性检查 | 各功能的业务 SQL 和事务规则 |
| 缓存基础设施 | 客户端生命周期、通用缓存原语 | 某个功能的键设计和失效业务规则 |
| 消息基础设施 | 发布订阅传输、确认、序列化约定 | 业务事件含义和业务流程 |
| 外部连接器 | 某个稳定外部协议的客户端和能力边界 | 本地业务规则和数据所有权 |

建立共享包应该至少满足一项条件：

1. 两个及以上调用方已经出现相同的基础设施需求。
2. 第三方协议本身构成可独立测试的稳定边界。
3. 该能力具有独立生命周期、安全边界或发布边界。

不得只因未来“可能复用”而创建 `common`、`utils`、`helpers`、`interfaces`、`implementations` 或全局 `adapter` 包。不得提交空包和占位目录。

### 4.3 依赖方向

典型应用的依赖方向如下：

```text
cmd/*  ->  transport  ->  feature packages
  |                         |
  +-------------------------+
  |
  +-> shared infrastructure packages
```

- 入口层装配所有依赖。
- HTTP、RPC、CLI 等传输层负责协议转换，不拥有业务规则。
- 功能包拥有业务规则和功能专属的数据访问。
- 共享基础设施包提供跨功能的技术能力，不反向依赖业务传输层。
- 业务包不得导入程序入口包。
- 出现循环依赖时必须重新判断所有权，不能通过全局包绕开循环。

不要规定“所有包必须通过接口或事件通信”。进程内简单调用优先使用具体类型；只有边界确实需要替换、隔离或异步化时才引入接口或事件。

## 5. 文件与包的拆分

### 5.1 文件拆分

- 默认从少量职责清晰的文件开始。
- 不为每个类型、方法或数据对象创建独立文件。
- 同一功能的持久化代码默认可以放在一个 `store.go` 中。
- 当单文件已经明显影响导航、测试定位或代码评审时，再按稳定能力拆分。
- 文件是阅读和维护单元，不是封装边界；同包文件拥有相同可见性。

### 5.2 包拆分

只有出现以下信号时才应该拆包：

- 子能力拥有独立且稳定的公共 API。
- 子能力被多个调用方复用。
- 子能力具有独立协议、生命周期、安全或发布边界。
- 当前包的依赖和所有权无法通过拆文件保持清晰。

拆包不得只为了减少行数。新包必须能用一句话描述唯一职责，并且不能依赖原包的内部实现细节。

## 6. 命名与可见性

### 6.1 包和文件

- 包名使用简短、全小写、无下划线的名称。
- 包名通常使用单数，并表达调用方理解的概念。
- 避免 `manager`、`processor`、`common` 等不能说明所有权的名称。
- 文件名使用小写下划线并按职责命名，例如 `validation.go`、`service_test.go`。
- 业务包的文件名和类型名不应包含可替换的数据库、缓存或消息中间件名称。
- 专门实现某个外部协议的包可以使用协议或产品名，因为协议本身就是该包的边界。

### 6.2 类型、接口和函数

- 名称必须表达概念或行为，不表达无意义的技术层级。
- 避免包名重复，例如使用 `order.Service`，而不是 `order.OrderService`。
- 不使用 `IStore`、`StoreInterface`、`ServiceImpl`、`RepositoryImpl`、`BaseStore` 或 `AdapterFactory`。
- 构造函数使用 `NewX`；包内只有一个主要类型且语义明确时可以使用 `New`。
- 获取值的普通方法不使用 `Get` 前缀，除非 `Get` 是业务动作、需要与其他查询区分，或符合既有 API 约定。
- 缩写保持一致，例如 `ID`、`URL`、`HTTP`、`API`，不写成 `Id`、`Url`。
- 布尔名称表达判断，如 `enabled`、`hasAccess`、`isReady`，避免含义不清的 `flag`。

### 6.3 导出与注释

- 默认不导出。只有跨包合法使用的名称才导出。
- 导出名称的注释应以该名称开头，并解释契约、约束或非显然行为。
- 不写重复代码字面的注释；优先解释为什么这样做、边界条件和安全要求。
- 不为测试导出内部细节；使用同包测试或通过公开行为验证。
- 公共 API 一旦形成跨包契约，修改时必须评估兼容性和所有调用方。

## 7. 接口与依赖注入

### 7.1 接口由消费者定义

接口应靠近消费者，只包含消费者实际需要的方法。可以在以下情况引入接口：

1. 消费者需要隔离外部 I/O 进行快速单元测试。
2. 已存在至少两个真实实现。
3. 外部系统、插件或进程边界需要稳定契约。

不得为每个结构体机械创建同名接口，不得为假设中的未来实现扩大方法集合。接口应尽量小；调用方只依赖其实际使用的能力。

### 7.2 参数和返回值

- 函数参数可以接受调用方需要的小接口。
- 构造函数通常返回具体类型，便于调用方使用完整、明确的 API。
- 需要隐藏实现且调用方只应看到稳定契约时，构造函数可以返回接口，但必须是有意设计，而不是机械规则。
- 不使用 `any` 绕过清晰类型，除非处理序列化、日志字段或真正开放的数据边界。

### 7.3 显式装配

依赖通过普通 Go 代码在程序入口显式创建：

```go
store := feature.NewStore(database)
service := feature.NewService(store)
handler := transport.NewHandler(service)
```

不使用依赖注入框架、全局 service locator、运行时反射装配或隐藏依赖初始化的 `init` 函数。

构造函数应验证无法在运行期恢复的结构性参数。构造完成的对象应立即可用；正常业务失败由方法返回。

## 8. 业务、存储与传输边界

### 8.1 Service

Service 适合负责：

- 输入规范化和业务校验。
- 业务状态转换。
- 跨多个存储操作或外部能力的用例编排。
- 返回与传输协议和数据库驱动无关的业务结果。

Service 不应负责：

- 解析 HTTP、RPC 或 CLI 请求。
- 生成协议状态码。
- 拼接 SQL 或处理数据库驱动错误。
- 读取进程环境变量。

没有业务编排价值时，不强制增加只做参数转发的 Service。

### 8.2 Store

功能专属 Store 适合负责：

- 查询和持久化数据转换。
- 写操作的事务边界。
- 存储驱动错误到稳定业务错误的映射。
- 维护软删除、版本、租户或作用域等一致查询条件。

Store 不应负责传输协议、页面展示、进程配置或无关功能的业务规则。功能专属 SQL 默认留在所属功能包中，不集中到全局数据库实现目录。

### 8.3 传输层

HTTP、RPC、CLI 等传输层负责：

- 路由、方法和协议字段解析。
- 请求体、响应体和大小限制。
- 协议级校验和认证信息提取。
- 调用业务能力。
- 业务错误到协议状态和稳定错误码的映射。

传输层不得直接访问数据库连接或执行 SQL。请求类型留在传输层，业务输入类型留在功能包。只有传输契约与业务类型确实不同、安全上需要隐藏字段或版本兼容需要隔离时，才创建 DTO 和显式转换，不机械生成 Mapper 层。

## 9. Context、并发与生命周期

- 可能阻塞、执行 I/O 或调用外部系统的函数，以 `context.Context` 作为第一个参数。
- 不把 Context 保存到结构体字段中，不传递 `nil` Context。
- 请求链继承上游 Context；后台任务使用可取消且通常带截止时间的 Context。
- 所有外部调用必须有超时，或继承一个已有截止时间的 Context。
- 不在不知道调用方需求时随意用 `context.Background()` 切断取消链。
- 启动 goroutine 必须明确所有者、停止机制、错误去向和资源上限。
- 禁止无法回收的后台 goroutine 和无界队列。
- 连接池、客户端和监听器等长生命周期资源由入口创建，并在退出时按顺序关闭。
- 共享可变状态必须有明确同步策略；使用竞态检测验证，但不能用检测工具替代设计。
- Channel 用于所有权转移、同步或流式传递，不把 Channel 当作默认容器。

## 10. 错误处理

- 可恢复失败通过 `error` 返回，不使用 panic 表达业务错误。
- 使用 `%w` 增加操作上下文，例如 `fmt.Errorf("save record: %w", err)`。
- 使用 `errors.Is` 和 `errors.As` 判断错误，不比较错误字符串。
- 包向调用方暴露稳定的领域错误或类型化错误，不泄漏驱动细节作为契约。
- 数据库错误码、第三方响应和系统调用错误在边界处映射。
- 错误文本使用小写开头、无句号，并说明失败操作。
- 面向外部的响应不得泄漏 SQL、内部路径、栈、凭据或第三方敏感详情。
- 忽略错误必须显式且合理。清理路径可以明确忽略已无处理价值的错误，业务路径不得静默丢弃错误。
- 只在真正无法继续启动或保持进程正确性时返回致命错误；库包不得调用 `os.Exit`。

## 11. 数据访问与事务

本节适用于使用数据库或其他事务存储的项目。

- 查询必须使用参数绑定，不拼接不可信输入。
- 动态表名、列名或排序字段必须来自受控白名单。
- 一个业务不变量涉及多次写入时，由拥有该用例的存储方法控制事务。
- 事务应尽量短，不在持有锁时执行不受控网络调用。
- 事务内所有操作使用同一个事务句柄。
- 失败路径回滚，成功路径显式提交；提交失败必须返回错误。
- 应用校验不能替代唯一键、外键、检查约束等最终一致性防线。
- Schema 变更使用有序、可审计的迁移；是否提供回滚迁移由项目发布策略明确规定。
- 应用启动通常不隐式修改生产 Schema；迁移由明确的发布步骤执行。
- 数据库管理员凭据与应用运行凭据必须分离，并遵循最小权限原则。
- 新查询和事务应有覆盖关键约束、并发和错误映射的集成测试。

## 12. 配置、日志与安全

### 12.1 配置

- 配置在进程入口加载、校验并通过显式参数传递。
- 业务包不重复读取环境变量或配置文件。
- 环境变量使用项目统一前缀，名称表达稳定语义。
- 默认值必须安全且适合目标环境；生产密钥不得存在代码或示例文件中。
- 真实凭据不得提交到版本库，应由 Secret 管理系统或运行环境注入。

### 12.2 日志

- 使用结构化日志和稳定字段名。
- 记录动作、对象标识、结果、耗时和可公开的错误分类。
- 不记录完整请求体、第三方响应或未经筛选的对象转储。
- 密码、Cookie、Token、Authorization Header、连接串、密钥和敏感业务数据不得写入日志。
- 日志级别应反映可操作性：预期业务拒绝通常不是服务端错误，进程无法继续才是致命错误。

### 12.3 输入与资源限制

- 对请求体、分页大小、批量数量、并发、队列、重试、响应体和外部调用设置上限。
- 所有不可信输入在边界校验，业务不变量在业务层再次保证。
- 重试只用于可重试错误，并设置最大次数、退避、抖动和总时限。
- 写操作重试必须考虑幂等键或等价的去重机制。

## 13. 测试规范

### 13.1 测试分层

- 单元测试验证纯业务规则、边界条件和错误语义，不依赖网络或真实中间件。
- Service 单元测试优先使用手写小替身，不默认引入大型 Mock 框架。
- 存储查询、事务、约束和迁移使用真实依赖的集成测试。
- HTTP/RPC 测试验证协议解析、状态、响应结构、错误映射和限制。
- 端到端测试只覆盖关键用户流程，不替代低层快速测试。
- 修复缺陷时必须在能稳定复现问题的最低合理层级增加回归测试。

### 13.2 测试质量

- 测试名称描述条件和预期行为，不逐行镜像实现。
- 测试相互隔离、可重复运行，不依赖执行顺序和生产数据。
- 优先使用表驱动测试覆盖同一行为的多组输入，但不要为了形式把不同场景强行塞入一张表。
- 时间、随机值和并发测试必须可控，避免无界等待和脆弱 sleep。
- 集成测试使用临时数据库、Schema、命名空间或容器，并可靠清理。
- 断言失败信息包含实际值和期望语义。
- 测试覆盖率是风险信号，不是唯一质量目标；关键不变量、失败路径和并发边界比追求行覆盖率更重要。
- 在持续集成中运行 `go test -race` 的合理范围，并定期执行完整竞态检测。

## 14. 代码质量与依赖管理

- 所有 Go 文件必须通过 `gofmt`。
- 提交前必须通过 `go test ./...` 和 `go vet ./...`；项目可增加静态分析器和安全扫描。
- 使用 `go mod tidy -diff` 或等价检查保持依赖文件一致。
- 新增依赖前评估维护状态、许可证、安全记录、体积和替代方案。
- 不用大型依赖解决少量标准库即可清晰完成的问题。
- 固定可复现的工具和构建版本；持续集成与本地质量门禁保持一致。
- 构建不得依赖开发者机器上的未声明文件、全局包或隐式网络状态。
- 生成代码必须标注来源和生成命令；评审其输入和边界，不手工修改可再生成文件。

## 15. 明确禁止的模式

- 全局 `models`、`services`、`repositories` 目录混放所有业务。
- 每个业务功能在全局数据库 adapter 下建立平行实现。
- `ServiceImpl`、`RepositoryImpl`、抽象基类、通用 CRUD 基类和泛型工厂。
- 没有真实消费者的接口和只有参数转发的包装层。
- `common`、`utils`、`helpers` 作为无所有权代码的收容目录。
- 通过包级可变全局变量、`init` 副作用或 service locator 传递依赖。
- 在传输层执行 SQL，或在存储层生成协议响应。
- 为尚不存在的数据库、中间件或部署方式预建通用适配层。
- 使用 panic、日志或进程退出代替正常错误传播。
- 在日志、错误或测试快照中保存凭据和敏感数据。

## 16. 评审清单

新增功能或大规模重构应逐项确认：

- [ ] 包名表达明确所有权，而不是技术层或模糊职责。
- [ ] 依赖方向单向且无循环。
- [ ] 接口由真实消费者定义，方法集合没有为未来需求扩张。
- [ ] 类型、接口和文件名未泄漏可替换的实现细节。
- [ ] 业务、传输、持久化和共享基础设施职责清晰。
- [ ] 事务覆盖完整业务不变量，存储约束提供最终防线。
- [ ] 错误已在边界映射，调用方不依赖驱动错误或错误字符串。
- [ ] Context、超时、资源关闭和 goroutine 生命周期明确。
- [ ] 输入、并发、重试和响应体有合理上限。
- [ ] 日志和错误响应不包含凭据或敏感载荷。
- [ ] 单元、协议、集成和端到端测试与变更风险相匹配。
- [ ] 没有为假设变化点增加 adapter、factory、DTO 或通用工具包。
- [ ] 格式化、静态检查、测试、依赖检查和构建全部通过。

## 17. 例外处理

本规范不阻止有证据的架构演进。采用独立 adapter 包、Ports and Adapters、多个 Module、代码生成框架或更严格分层时，变更说明必须回答：

1. 当前已经出现了什么真实问题或变化点。
2. 新结构如何降低当前复杂度或建立必要边界。
3. 依赖方向、测试策略、兼容性和迁移成本是什么。
4. 为什么更简单的包内实现不足以解决问题。
5. 哪些项目文档和质量门禁需要同步更新。

无法回答这些问题时，默认继续采用更简单的 Go 结构。
