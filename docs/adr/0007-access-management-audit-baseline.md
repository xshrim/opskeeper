# ADR-0007：T05 使用 Scope 组、权限子集授权、revision 缓存和追加式审计

- 状态：已接受，T05 已完成
- 日期：2026-08-16

## 背景

T04 已建立仅允许的三级 RBAC，但角色绑定只能由受控 bootstrap 和测试建立。T05 需要提供用户、用户组和角色绑定管理，同时保证授权人不能转授自身没有的权限，并让权限变更及时影响所有后续请求。

## 决策

1. 用户组绑定一个 Scope，组成员通过组上的角色绑定获得权限；组成员变更和组停用都递增授权版本。
2. 用户状态管理限定为 PlatformAdmin；团队和项目管理员只能管理其 `member:grant` 范围内的组成员和角色绑定。
3. 创建角色绑定前，服务端检查授权人对目标 Scope 拥有 `member:grant`，并且对待授予角色的每个权限点都拥有有效权限。数据库继续校验角色 Scope 类型与绑定 Scope 类型一致。
4. PostgreSQL 保存单调递增的 `authorization_revision`。Redis 缓存键包含该版本号，用户、Scope、组、成员、角色、角色权限和角色绑定的任何变化都会生成新版本键；缓存错误只回源权威数据库，不沿用旧缓存结果。
5. 审计事件只追加写入 PostgreSQL，记录用户状态、登录、会话刷新/失效、组成员和角色绑定变化。敏感凭据不进入审计详情；来源 IP 使用 HTTP 可信代理解析结果。

## 后果

- 管理 API 不需要相信前端传入的角色范围，所有转授规则在服务端重新计算。
- revision 机制避免依赖跨实例 Redis `DEL` 成功与否来保证撤权生效；旧缓存键可自然过期，不会被新请求使用。
- 用户管理、组管理、角色绑定和审计查询仍属于模块化单体的明确领域边界；不预建全局 adapter 层。
- T05 不提供 OIDC/LDAP、自定义角色编辑器、显式拒绝策略和 PostgreSQL RLS。
