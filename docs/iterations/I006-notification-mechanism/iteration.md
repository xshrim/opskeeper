# I006 通知机制

**迭代编号：** I006
**目录标识：** I006-notification-mechanism
**状态：** 实施中
**计划开始：** 2026-09-30
**计划封板：** 待定

## 1. 迭代目标

建立独立、可复用、可审计的通知机制，为巡检策略提供可靠的异常、恢复和系统事件通知。通知页面统一管理通知渠道、通知规则、通知模板和投递记录；巡检策略只选择可复用的通知规则，不重复维护渠道、模板和投递逻辑。

本迭代以 PostgreSQL 作为通知消息队列。巡检状态变化、通知事件和投递任务通过同一数据库事务提交，再由投递 Worker 发送到渠道。消息队列后端通过 `OPSK_MESSAGE_QUEUE_BACKEND` 配置，当前唯一支持的值为 `postgres`，默认值也是 `postgres`；其他后端只有在后续容量或隔离评估通过后另立 ADR 实施。

## 2. 迭代范围

- 在权限菜单上方增加通知菜单和通知页面；
- 管理通知渠道、渠道凭据、渠道测试、启停和限流；
- 管理可版本化通知模板、变量契约、预览和发布；
- 管理事件匹配、严重级别、冷却、聚合、静默时段和渠道/模板路由规则；
- 在巡检策略中关联通知规则，并在当前 Scope 和权限范围内选择；
- 为异常新建、重新打开、严重级别变化、恢复、巡检失败和能力不可用事件建立统一事件模型；
- 修复当前通知在巡检事务提交后才入队、恢复事件未入队以及重复异常重复投递的问题；
- 使用 `notification_deliveries` 持久化队列表、租约、`FOR UPDATE SKIP LOCKED`、`LISTEN/NOTIFY` 和轮询兜底实现可靠投递；
- 复用锁定版本的 Notify provider 清单，提供 provider 注册表、配置 Schema 和统一消息适配；
- 记录投递尝试、失败原因、重试、死信和手动重试审计。

## 3. 关键设计决策

1. **规则和模板属于通知中心。** 它们是可复用治理对象，不放入巡检策略正文。策略只保存规则关联；创建策略时可通过快捷入口创建并回填规则。
2. **投递快照不可变。** 入队时保存事件、规则命中结果、模板版本、渠道配置版本和变量快照；后续编辑规则、模板或渠道不会改变已排队消息。
3. **PostgreSQL 默认队列不需要扩展。** 使用 `notification_deliveries` 普通队列表、事务写入、行级租约、`FOR UPDATE SKIP LOCKED` 和原生 `LISTEN/NOTIFY`。`LISTEN/NOTIFY` 仅用于唤醒，不承担持久化；断线、通知合并或丢失时由定时轮询补偿。`pgmq` 不是当前基线，因为它不是 PostgreSQL 内置扩展，当前部署镜像和受限迁移角色也不能假设可创建实例级扩展。
4. **队列配置不静默回退。** 启动时校验 `OPSK_MESSAGE_QUEUE_BACKEND`，当前除 `postgres` 外的值均拒绝启动，不自动切换后端；未来新增后端时必须单独定义健康检查、积压指标和回滚策略。
5. **凭据只属于渠道。** provider 配置和密钥加密存放在通知渠道对象中，API 只返回脱敏摘要，不建立可被其他业务共享的独立通知凭据表。
6. **范围显式共享。** 渠道、规则和模板默认只在创建 Scope 可用；需要下级使用时由管理员显式开启“对子 Scope 可用”，不跨团队隐式共享。

## 4. 非目标

- 不在本迭代实现自动修复、自动扩缩容或由通知回调触发资源变更；
- 不允许模板、provider 配置或外部响应执行任意代码、SQL、Shell 或资源命令；
- 不把通知规则、模板正文或渠道凭据放入 Skill、巡检目标或模型上下文；
- 不把外部消息队列或 `pgmq` 作为本迭代部署依赖；
- 不在未经过预览和用户确认前直接冻结通知页面的视觉方案；
- 不为兼容旧 Webhook 结构长期保留第二套通知业务模型，迁移后由新通知模块统一读写。

## 7. 进入条件

- I003 Engine 的 Scope、权限、审计和资源上下文边界可复用；
- 当前巡检 Scheduler、Worker、Finding、运行状态和 PostgreSQL Job Queue 可作为迁移基础；
- Notify 依赖版本、provider 支持矩阵和各 provider 的凭据字段完成锁定；
- 明确通知事件只来自已提交的巡检状态变化，不从前端或模型输出直接创建投递；
- 确认 PostgreSQL 16 环境允许应用连接执行 `LISTEN/NOTIFY`，但迁移角色不需要创建额外扩展；
- 已明确 `OPSK_MESSAGE_QUEUE_BACKEND` 默认值为 `postgres`，当前不启用其他队列中间件。

## 8. 退出条件

- 通知页面可在当前组织 Scope 和权限下管理渠道、模板、规则和投递记录；
- 巡检策略只关联通知规则，事件规则和模板能够被多个策略复用；
- Finding 新建、重新打开、严重级别变化和恢复只按状态变化发送，重复未变化观察不会重复提醒；
- 运行失败和能力不可用事件可按规则路由，恢复通知可关联原始事件；
- PostgreSQL 队列通过事务提交、租约、`SKIP LOCKED`、`LISTEN/NOTIFY` 和轮询恢复验证；
- 失败投递有有限重试、退避、死信、手动重试和审计，敏感信息不进入日志或前端；
- 渠道凭据加密保存，API 和列表只返回脱敏信息，测试发送受独立权限保护；
- 后端单元、数据库集成、并发、API、前端检查、构建和主要 Playwright 场景通过；
- 验收报告记录每项证据，未完成内容转入 backlog 或后续迭代。
