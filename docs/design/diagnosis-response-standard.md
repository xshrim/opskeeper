# AI 诊断回答范式

**版本：** v1

**适用范围：** AI 诊断对话、诊断复查和由诊断适配器发起的 Agent 执行

## 1. 结论

AI 诊断需要一套稳定的回答契约，但这套契约不应该只存在于一个可选 Skill 中。

| 层 | 负责内容 | 是否必须 |
|---|---|---:|
| AIEngine | ReAct 循环、工具授权、事件顺序、取消、预算和审计 | 是 |
| 诊断回答契约 | 进度表达、证据与推断边界、最终回答结构、Markdown 选择 | 是 |
| 资源 Skill | PostgreSQL、Kafka、Kubernetes 等领域知识、工具和阈值 | 按资源选择 |
| AgentProfile | 特定团队或专家角色的额外约束 | 可选 |

因此，回答范式应该由诊断适配器作为基础指令注入；资源 Skill 和 AgentProfile 只能补充它，不能取消事实核验、错误纠正和格式要求。

## 2. 交互协议

诊断过程遵循以下循环：

```text
用户问题
  -> 当前判断与核验目标
  -> 工具调用
  -> 工具观察结果
  -> 更新判断 / 修正路径
  -> 继续调用或输出结论
```

对用户可见的阶段性文本应该是自然语言，例如：

> 用户反馈 API 响应慢。我先确认应用是否有活动实例、错误日志和资源瓶颈，再判断问题位于应用层还是数据库层。

工具调用后应该紧接着说明结果的意义：

> 数据库当前连接利用率为 18%，没有锁等待和慢查询。数据库不是当前证据下的直接瓶颈，我继续检查应用容器和连接池日志。

不使用固定的“阶段 1、阶段 2”话术，不重复已经发送过的进度，也不把隐藏思维链完整展示给用户。公开的是脱敏、限长、面向行动的 reasoning summary。

## 3. 证据规则

每个结论都应落在以下三类信息之一：

- **用户事实：** 用户明确提供的现象、时间范围、请求或约束。
- **环境事实：** 工具返回的日志、指标、配置、代码、Git 状态、容器状态或编译/测试结果。
- **推断：** 基于事实得出的可能原因，必须使用“可能”“更可能”“推测”等措辞，并说明依据。

工具错误、空结果、权限拒绝、超时和部分结果本身也是证据，不能静默丢弃。发生错误时，Agent 应重新评估：修正参数、缩小范围、改换工具、重试一次或明确说明无法核验。

## 4. 最终回答结构

最终回答不是固定模板，而是按问题复杂度和信息形态选择结构：

### 简单问题

直接给出结论和必要依据，不强行添加标题。

### 一般诊断

直接回答用户的问题。只有确实存在相应内容时，才增加结论、证据、建议或待核验等小节；不要求固定顺序，也不输出空小节。

只保留有内容的小节。如果证据和结论很短，可以合并为两段文字；只要最终回答包含两个及以上主题，使用 `##` 二级标题分段。标题应简短且描述具体内容，例如 `## 结论`、`## 关键证据`、`## 建议`，不要使用“回答”“分析”等空泛标题。

### 复杂诊断

当存在多个对象、时间点或候选根因时，使用“现象 -> 证据 -> 判断 -> 建议 -> 风险”结构，并用表格比较对象：

```markdown
| 检查项 | 结果 | 解释 |
|---|---:|---|
| 连接利用率 | 18% | 暂无连接耗尽证据 |
| 锁等待 | 0 | 暂无锁阻塞证据 |
```

## 5. Markdown 选择规则

| 内容类型 | 推荐 Markdown |
|---|---|
| 一段直接说明 | 普通段落 |
| 章节较多 | `##` / `###` 标题 |
| 并列事实 | 无序列表 |
| 操作顺序、优先级 | 有序列表 |
| 多个对象或指标横向比较 | 表格 |
| 命令、SQL、JSON、配置、代码、日志 | 带语言标记的围栏代码块 |
| 单个变量、状态、工具名 | 必要时使用行内代码或加粗 |

最终回答只有一句结论或两个短段落时可不用标题；只要存在两个及以上主题，必须使用 `##` 二级标题。`###` 仅用于一个主题下确有多个子项时，不能跳级、连续堆叠标题或创建没有正文的标题。执行过程中的进度说明保持自然段，不按每次工具调用创建标题。

行内代码只用于短标识符、字段名、工具名、命令片段或精确值；普通描述不要包在代码标记中。不要把每一行都写成列表，不要把标题或代码包在不匹配的 Markdown 标记中，不要为了“看起来结构化”而给只有一项的内容套表格。当内容具有明确语义时，优先在标题或关键结论前使用少量图标符号增强扫描性：`✅` 表示已确认/结论，`⚠️` 表示风险/待核验，`❌` 表示失败/阻断，`🔎` 表示证据/检查，`🔧` 表示处置/修复，`📊` 表示指标，`📅` 表示时间范围，`🧭` 表示下一步。例如 `## ✅ 结论`、`## 🔎 关键证据`、`## 🔧 建议`。图标必须与文字语义一致，不能替代事实、状态或结论；简单回答不必强行加图标，也不要每行堆叠图标。

推荐图标词典：`📋` 用于检查清单/待办项，`🧪` 用于测试/验证/复现，`⏱️` 用于耗时/超时/性能，`📈` 用于趋势/增长/变化，`🗂️` 用于资源/对象/配置，`🔗` 用于关联/依赖/引用，`🔒` 用于权限/安全/凭据，`♻️` 用于重试/恢复/回滚，`🚦` 用于状态/阶段/门禁，`📌` 用于重点提醒，`💡` 用于解释/优化思路，`🚀` 用于执行/发布/上线，`🛑` 用于阻断/不可继续。优先把图标放在小节标题或小节首句前，每个标题最多使用一个主图标；不要把同一图标重复添加到每个列表项。例如 `## 📋 检查清单`、`## 🧪 验证结果`、`## ⏱️ 性能与耗时`、`## 🔒 权限与安全`、`## ♻️ 恢复与重试`。

## 6. 建议的回答检查清单

模型在结束前应自检：

1. 是否直接回答了用户的问题？
2. 结论是否有工具事实或用户事实支撑？
3. 事实、推断和待核验项是否分开？
4. 工具错误或空结果是否被正确处理？
5. 建议是否包含优先级、实施前提和验证方法？
6. 是否选择了最适合内容的 Markdown，而不是把所有内容变成列表？
7. 是否避免重复进度、暴露隐藏思维链或声称执行了未执行的变更？

## 7. Skill 与 AgentProfile 的使用方式

资源 Skill 示例：PostgreSQL Skill 只补充连接、锁、慢查询、容量等领域检查项，以及对应工具的输入约束；它不重复定义最终回答格式。

团队 AgentProfile 示例：可以补充“面向 SRE，优先给出可观测性证据”和“建议必须附回滚方案”等要求；它仍必须服从本范式的证据边界和 Markdown 规则。

只有在需要跨多个业务场景复用同一套领域知识时才创建 Skill。回答排版和诊断叙事属于基础契约，应由诊断适配器默认启用。
