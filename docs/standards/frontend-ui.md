# 前端 UI 与交互规范

本文是 OpsKeeper 前端页面设计、实现和评审的强制性规范，适用于 `frontend/` 下的所有页面、组件和交互。规范的核心目标是：**极致简洁、结构清晰、交互明确、体验友好**。拒绝无意义的装饰，追求零学习成本的直觉化操作。

## 1. 整体视觉与布局

### 1.1 色彩

- 全局主色不超过两种：一种中性冷色作为主色和文字色，搭配一种高饱和品牌/操作高亮色。
- 背景统一使用纯白或微灰（例如 `#F8FAFC`）。
- 禁止复杂渐变背景和高对比度的杂色组合；状态颜色只用于表达状态，不作为装饰。

### 1.2 视觉层级

- 页面必须划分为明确的功能区块，例如顶部导航、主操作区、侧边辅助区和底部状态栏。
- 区域之间使用 8px 网格倍数留白（如 `16px`、`24px`、`32px`）或极淡的分割线（如 `#E2E8F0`）区分，避免拥挤。
- 卡片和容器禁止重阴影，优先使用 1px 细边框或微弱柔和的阴影，例如 `0 1px 3px rgba(0, 0, 0, 0.05)`。
- 页面结构优先使用清晰的栅格和对齐关系，不使用装饰性容器堆叠信息。

### 1.3 排版

| 层级 | 字号/字重 | 用途 |
|---|---|---|
| 标题 | `18-20px` / Bold | 页面和主要区块标题 |
| 副标题/区域头 | `14-16px` / Medium | 次级区块标题 |
| 正文 | `14px` / Regular | 主要内容和表单文字 |
| 辅助/提示 | `12px` / Regular | 说明、状态和辅助信息 |

正文和长文本行高固定在 `1.5-1.6`，避免因内容长度变化造成布局跳动或难以阅读。

## 2. 表单与输入交互

### 2.1 占位符与说明

- 所有输入框必须提供清晰的 `placeholder`，提示格式或典型示例，例如“例如：`example@domain.com`”或“请输入 1-100 之间的整数”；不能只提供空输入框。
- 复杂或易混淆的字段必须在标签旁提供问号图标和 Tooltip，悬停或聚焦时展示用途、格式和示例。
- Label 必须与对应控件关联；不能只用 placeholder 代替标签。

### 2.2 防错与实时校验

- 校验应在输入或失焦时及时触发，错误信息直接显示在对应输入框下方，使用高亮红色（如 `#EF4444`）。
- 错误提示必须明确说明如何纠正，不能只显示“格式错误”或“无效输入”。
- 数字、电话、日期等特定输入优先使用限制性控件（数字输入框、日期选择器）或输入屏蔽，从源头减少无效输入。
- 提交前保留完整校验；服务端校验失败时，将错误定位回对应字段或表单区域。

## 3. 操作反馈与状态感知

### 3.1 操作层级

- 每个页面或功能区只保留一个最突出的主按钮（Primary Button）。其他操作使用次级按钮或文本按钮，避免多个高亮按钮争夺焦点。
- 条件不满足时，主操作按钮必须呈明确禁用状态；悬停或聚焦时通过 Tooltip 告知原因，例如“请先填写必填项”。对于原生禁用控件，Tooltip 应绑定到可获得悬停事件的外层元素。
- 不熟悉的纯图标按钮必须提供 Tooltip；删除、保存、刷新、缩放等通用符号可使用图标按钮，但仍须具备可访问名称。

### 3.2 加载与结果

- 任何耗时操作（异步请求、提交表单、导入、诊断或审批）必须立即反馈：按钮切换为 Loading 状态，或在内容区域展示 Skeleton/进度状态。禁止界面静止无响应。
- 成功操作使用轻量 Toast，显示绿色提示并在 2-3 秒后自动消失。
- 失败操作使用红色提示，并保留手动确认、重试或返回入口；错误信息必须说明下一步动作。
- 操作期间禁止重复提交；完成后应同步更新相关列表、详情和状态，不要求用户盲目刷新。

### 3.3 破坏性操作

删除、覆盖、重置等不可逆操作必须弹出 Modal 二次确认，明确说明后果，例如“删除后数据不可恢复，确定继续吗？”。确认按钮应使用明确的破坏性语义，取消操作应始终可见。

## 4. 空状态与异常处理

### 4.1 空状态

列表或图表无数据时，不得留白或只显示“暂无数据”。必须展示简约的图标/插画、一句简短说明以及下一步引导按钮，例如“暂无任务，点击下方按钮创建第一个任务”。

空状态应区分“尚未创建”“筛选无结果”和“暂无权限”，并提供对应的清除筛选、创建或申请权限入口。

### 4.2 网络与系统错误

页面加载失败时，必须提供清晰的错误提示和一键“刷新/重试”入口。错误状态不能覆盖原有页面上下文，用户重试后应保留作用域、筛选条件和已填写但未提交的内容（涉及敏感信息时遵循安全策略）。

## 5. 响应式与可访问性

- 所有可点击元素（按钮、卡片、列表项、链接）必须包含明确的 Hover 和 Active 视觉变化，例如轻微变深、背景变化或指针变为 `pointer`。
- 支持 Tab 键顺畅切换输入焦点；当前 Focus 元素必须有清晰可见的焦点样式，不能仅依赖鼠标操作。
- 核心流程必须可以仅使用键盘完成，焦点顺序应符合页面阅读和操作顺序。
- 控件、状态和异步变化应提供语义标签、可访问名称和必要的状态播报；不能只依赖颜色、图标或位置表达含义。
- 布局必须适配桌面和窄屏视口，内容、按钮和文字不得重叠或产生页面级横向溢出。

## 6. 实施与验收

- 新增或修改页面时，需求和验收记录必须覆盖加载、空数据、错误、禁用、提交中、成功和失败状态。
- UI 评审至少检查桌面与窄屏视口、鼠标与键盘操作、表单校验、重复提交保护和破坏性操作确认。
- 关键交互应通过 Svelte 单元/组件测试或 Playwright 场景固定；视觉变化不能替代行为验收。
- 若现有页面暂时无法满足本规范，必须在对应迭代需求中明确差距、改进任务和验收标准。

## 7. 持续设计与方案评审约束

- 前端页面必须逐页重新设计和评审；不得以一次性全局改版替代对单个页面信息架构、操作路径和状态反馈的具体设计。
- 每次提交一个页面的设计方案时，至少提供三种有实质差异的风格与布局方案供选择。每种方案必须说明视觉语言、信息层级、主要操作位置、核心交互方式、响应式表现和可访问性影响，并列出适用场景与取舍。
- 未经用户确认，不得将某个方案视为最终设计或直接以该方案完成页面实现。确认结果必须记录在对应迭代/需求或页面设计记录中。
- 一旦前面的页面样式和布局被确认，后续页面必须继承已确认的设计令牌和模式，包括色彩、字体、间距、圆角、边框、阴影、控件状态、导航结构和反馈方式；除非提出新的方案并重新获得确认，不得另起一套视觉风格。
- 在整体风格已经统一的前提下，后续每个页面仍需提供三种以上符合本规范的排版布局和交互方式供选择。候选方案可以调整信息分组、密度、导航路径和操作编排，但不得破坏已冻结的视觉令牌、可访问性和状态反馈规则。
- 方案比较应优先围绕用户任务完成效率、信息可扫描性、错误恢复和窄屏可用性，不得以装饰数量、视觉复杂度或实现炫技作为主要评价标准。
- 已确认的方案、未采用方案及选择理由应保留简短记录，作为后续页面设计和迭代验收的依据，避免反复讨论已经确定的决策。
